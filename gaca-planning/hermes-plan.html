The Committed Plan

Hermes drives. The API layer holds the keys.

The decision is made: Hermes is the agent, running on its own box, stood up by hand and documented step by step in the Hermes Setup log. It is no longer a placeholder for something we intend to write. The remaining work is deliberately small and singular — add an approval and event layer to the existing API, and drive it from the Android app. That one addition is what turns a capable agent into a controlled one, because it moves the permission to act out of the agent and into a layer that answers to a phone tap.

Agent: Hermes (committed) New work: approvals + events Hermes → external: read only Writes live in the API layer Control surface: Android app
The plan in one line Hermes reads widely and writes almost nothing; it composes drafts and proposals and files them as events. The API layer holds every privileged write credential and executes only what the operator approves from the phone. Capability is separated from intent — the agent decides what should happen, a human decides whether it happens, and a third component is the only thing that can make it happen.

The architecture

The permission model

This table is the plan. Everything else is detail.

From → toReadWriteNote
Hermes → external apps (email, third-party)YESNOIt can read your mail and draft a reply. It cannot send one — the sending credential is not on that box.
Hermes → personal apps (calendar, ours)YESYESApps we built, exposing a scoped, revocable agent token. Blast radius is our own data.
Hermes → API layerLIMITEDLIMITEDA deliberately narrow surface: file an event, raise an approval request. Nothing else.
API layer → HermesYESYESThe API drives Hermes — starts runs, reads transcripts and internals. The relationship is asymmetric on purpose.
API layer → external apps & write MCPsYESYESEvery privileged write lives here, and fires only on an approved action.
Phone → API layerYESYESMessages, approvals, events. The only human-facing surface.
Why this beats an approval policy Most agent approval systems are advisory: the agent holds the credential and is asked to pause before using it. That fails exactly when it matters — a confused agent, a bad plan, or a prompt injection buried in an email it was told to summarise.

This design is architectural instead. Hermes does not pause before sending email; it cannot send email at all, because the credential is in a different process behind a different trust boundary. The worst outcome from a compromised or mistaken agent is a bad proposal that a human declines. That is a categorically smaller failure than a bad action already taken — and it matters most precisely because Hermes reads untrusted content for a living.

What we're building

One layer, two resources, added to the API that already exists.

Events — the timeline

An append-only record of what the agent did, saw, and proposes. Hermes files events through its narrow surface; the API sequences and persists them, then fans them out to the phone over the SSE stream already built.

This is the observability the Overview called for from day one — every tool call and decision visible — and it doubles as the feed the app renders.

Approvals — the gate

A proposed action carrying everything needed to judge it: what, against which target, with what payload, and why. It sits pending until the phone answers. On approve, the API layer executes it with its own credentials; on deny, it closes unexecuted.

None of the decision is delegated back to the agent. Hermes learns the outcome as an event like any other.

The one open design question Hermes needs a way to reach the API layer to file events and raise approvals — which the sketch notes plainly: "probably needs more than API to fire events." Two candidate mechanisms, and this is the first thing to settle at build time:

(a) A skill. Give Hermes a SKILL.md plus an operator-minted token — exactly the agent-ready pattern already working for the calendar app (Setup, Step 10). Nothing new to invent, and the narrow surface is enforced by the token's scope.

(b) A write MCP. More structured tool definitions, but another moving part to run and secure.

(a) is the recommendation — it reuses a pattern already proven on this stack, and keeps the agent's view of the API layer as just another agent-ready app.

How replies reach the phone

This part is already designed and built, and does not change. Worth restating because one move in it is non-obvious.

Why there is a hand-off at all SSE is one-directional — server → client. The phone can receive on its event stream but cannot send on it. So "send a message" and "receive replies" are always two connections: a long-lived GET …/events and a short POST …/messages. The POST triggers a run, but the run's output must return on the other connection — a different handler, a different coroutine. A small bus carries events from the run-reader to the open stream.
  1. The phone opens its stream (GET /sessions/{id}/events) when the chat screen loads, and leaves it open.
  2. You type → the phone POSTs. The handler persists the message, starts a Hermes run, spawns a background reader, and returns 202.
  3. The reader task consumes Hermes' SSE, translates each frame to a neutral GacaEvent, persists it to SQLite, and publishes it to the bus.
  4. The events handler, subscribed the whole time, relays each one down the phone's open socket.
  5. Approvals ride the same rails — a pending approval is an event, the phone renders it as a prompt, and the answer returns as an ordinary POST.

Redis pub/sub does the fan-out; SQLite is the durable record, so a reconnecting phone replays by Last-Event-ID and then attaches live. Approvals in particular must survive a dropped connection — an approval that vanished because the phone slept would be a bad failure — which is exactly why the record is durable and the transport is not trusted.

What already exists

The spine is built and proven end to end. This plan adds to it rather than starting anything.

The API and its store

Sessions, messages, SSE with Last-Event-ID replay, SQLite as the record, and the publish/subscribe bus.

The Hermes adapter

AgentBackend port, the adapter, and the SSE translator — verified against a live gateway. Round trip proven by curl.

A working agent

A configured Hermes box: model, web, repos, memory, a second host, and a build skill. See the Setup log.

The adapter seam stays because it is already written and costs nothing to keep — but this plan commits to Hermes. The seam is insurance now, not a roadmap.

Build order

Smallest path to a working approval loop
  1. Define the two schemas — Event and Approval — as neutral types alongside the existing GacaEvent. Contract first.
  2. Add the routes: list and file events; list, raise, and answer approvals. Persist to SQLite, publish to the bus.
  3. Give Hermes its narrow surface — a skill plus a scoped token that can do exactly two things: file an event, raise an approval.
  4. Add one executor in the API layer behind the gate. Email send is the obvious first, since it is the case that motivated the split.
  5. Render it on the phone: the event timeline, and a pending approval with approve/deny.
  6. Then widen: more executors, more write MCPs, all behind the same gate.
Step 4 is the proof. When a draft composed by an agent that cannot send it appears on your phone, is approved with a tap, and is sent by the API layer — the architecture is real.

Locked decisions

Honor these
  1. Hermes is the agent. Committed, not provisional. It runs as a localhost daemon on its own box; the API reaches it as an HTTP client.
  2. Hermes gets read access to external applications, never write. It composes drafts, suggestions, and proposals. It does not act on the outside world.
  3. Every privileged write credential lives in the API layer. If the agent could hold it, it is in the wrong place.
  4. Personal applications are the deliberate exception. Apps we built ourselves may grant Hermes a scoped, revocable agent token for direct writes.
  5. Hermes' access to the API layer is a narrow, explicit surface — file events, raise approvals. It is not a general client of our own API.
  6. The API layer has read/write access to Hermes and its internals. The relationship is asymmetric by design.
  7. No privileged write executes without an approval recorded and answered by the operator.
  8. The phone is the control surface. Messages, events, and approvals; nothing should require a terminal.
  9. SQLite is the durable record; the bus is ephemeral. Approvals and events survive reconnects and replay by Last-Event-ID.
  10. The scope is this and no more for now. The approval/event layer is the whole of the next build.

The committed plan: Hermes as the agent, an approval and event layer added to the existing API, and the Android app as the control surface. The permission split — broad read for the agent, every privileged write behind a gate in the API layer — is the load-bearing idea, and it is enforced by where credentials live rather than by asking the agent to behave. Setup of the Hermes box is documented step by step in the Hermes Setup log; the Overview holds the original build-vs-buy study this grew out of.
