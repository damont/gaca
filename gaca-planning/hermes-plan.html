Own the shell, adopt the engine — GACA over Hermes

The plan we're actually building first. Keep the GACA API and the native app exactly as designed in the Full GACA Plan, but instead of writing our own agent loop now, put Hermes Agent behind an adapter as the agent-loop backend. The API's routes and service layer never learn the word "Hermes"; a future gaca-agent drops in behind the same port without touching the routes, the services, or the Android app. This page locks the seam, the read path, the transport, and the build order.

Engine: Hermes Agent (adopted, swappable) Shell: GACA API + native Android (ours) Pattern: ports & adapters Transport: Redis pub/sub (fan-out only) Record: SQLite Hermes API: localhost:8642
The decision in one line GACA owns the shell (the API contract, auth, the audit/event timeline, the Android app); Hermes is the engine (the loop, tools, memory, skills, scheduler, subagents) — adopted now, behind an adapter, so it's reversible. This deliberately inverts the GACA Experiment's "own the loop" thesis in exchange for getting a capable assistant fast. The adapter is what makes that a loan, not a marriage: when we're ready to own the loop, we write a second adapter and flip a config value.

Why Hermes fits behind our API

The reason this is clean and not a scraping project: Hermes ships a first-class HTTP API (its api_server gateway adapter) whose shape is almost a mirror of the async contract we already designed — 202-style run handles, an SSE event stream, structured per-tool events, and externally-addressable sessions. We connect to it as an HTTP client; we do not read its database or embed it in-process.

The seam — ports & adapters

One principle makes the swap real and is the rule every reviewer should hold us to:

The rule The adapter produces neutral GACA events. The service layer sequences, persists, and fans them out. Everything Hermes-shaped is quarantined inside agent/hermes/. The test is mechanical: grep -ri hermes gaca_api/ --exclude-dir=hermes must return nothing. If a Hermes type or endpoint name (assistant.delta, /v1/runs, X-Hermes-Session-Id) appears in a router, a service, or the app, the abstraction has leaked.

Two ports live in the agent layer. The routers and services depend only on these:

AgentBackend port

class AgentBackend(Protocol):
  async def start_run(session, message) -> RunHandle
  def     stream_events(run) -> AsyncIterator[GacaEvent]
  async def stop_run(run) -> None
  async def submit_approval(run, decision) -> None
  def     capabilities() -> Capabilities

HermesAdapter implements it: start_run → POST /v1/runs; stream_events → consume Hermes' SSE and yield translated neutral events; submit_approval → POST /v1/runs/{id}/approval. A future GacaAgentAdapter implements the same five methods.

MemoryBackend port

class MemoryBackend(Protocol):
  async def search(scope, query) -> list[Memory]
  async def write(scope, item) -> None
  async def load_session(sid) -> WorkingSet
  async def flush_session(sid) -> None

Memory is handled in the agent layer, behind this port. Phase 1: the HermesAdapter implements it by reading Hermes' own memory — its HTTP API if one exists, otherwise its memory_store.db on disk. Later, a gaca-memory adapter slots in behind the same port with no route or service change.

What stays in the invariant core (never changes on swap) Event sequencing (monotonic per-session id for Last-Event-ID resume), persistence to SQLite, fan-out to subscribers, the audit log, auth, and every HTTP route. The adapter only produces raw neutral events; the core does everything durable and client-facing with them. That split is why a new engine costs one new adapter, not a rewrite.

The read path — how replies reach the phone

This is the part worth drawing, because it has one non-obvious move. The cause of that move is a plain fact about the transport:

Why there's a hand-off at all SSE is one-directional — server → client only. The phone can receive on its event stream but cannot send on it. So "send a message" and "receive replies" are always two separate connections: a long-lived GET …/events (receive) and a short POST …/messages (send). The POST is what triggers a Hermes run, but the run's output must come back down the other connection — a different request handler, a different coroutine. A small in-process router (over Redis) carries events from the run-reader to the open event stream. This is inherent to the async contract we already chose — not something Hermes adds.

The same path in words

  1. The phone opens its receive stream (GET /sessions/{id}/events) when the chat screen loads and leaves it open. The events handler subscribes to bus[session]. Nothing flows yet.
  2. You type → the phone POSTs (POST /sessions/{id}/messages). The handler saves the message to SQLite, calls Hermes POST /v1/runs (with X-Hermes-Session-Id = the mapped id), gets a run_id back, spawns a background read_run task, and returns 202. The POST is now finished — fast, non-blocking.
  3. The read_run task opens Hermes' GET /v1/runs/{run_id}/events SSE. For each Hermes event it does three things: translate to a neutral GacaEvent, persist it to SQLite, and publish it to bus[session] (Redis).
  4. The events handler, subscribed the whole time, drains each published event and writes it down the phone's open SSE socket. The phone renders it live.
  5. When Hermes sends done, the read_run task ends. The receive stream stays open for the next message.

So your original mental model — "our API opens a connection to Hermes' SSE and pipes it back" — is right. The only addition is that the pipe can't go straight to the phone, because the phone's listening socket and the POST that started the run are two different connections. The bus is the ~20-line bridge between them.

Transport — Redis pub/sub, fan-out only

Decision Use Redis pub/sub now for the read_run → events-handler hand-off — and only that. Do not build the Redis Streams dispatch/inbox/consumer-group layer yet.

Why adopt it now

  • It's the same code as an in-process bus (publish/subscribe), just pointed at Redis — not more to write.
  • It removes the single-worker constraint permanently: the read_run task and the events handler can live in different API workers and still connect.
  • It's exactly the piece the Full GACA Plan keeps for fan-out — so this code survives the eventual swap with no rewrite.
  • Cost is one redis.service systemd unit already in the stack.

Why not the Streams layer yet

  • Dispatch stream + per-session inbox + supervisor lifecycle existed to route, order, and keep sessions alive.
  • Hermes already does all of that (X-Hermes-Session-Id + state.db + max_concurrent_runs).
  • We only rebuild it when gaca-agent owns the run lifecycle itself and needs durable, crash-safe handoff.

Redis pub/sub is ephemeral — if no subscriber is connected at publish time, that event is dropped from the live path. That's why SQLite stays the durable record: every event is persisted as it's published, and a reconnecting phone replays from SQLite by Last-Event-ID, then attaches to the live channel. SQLite is embedded and file-based — no separate service or port to run, backups are a single file copy, and objects stay natural via Pydantic (store the model as JSON in a column, load with model_validate_json()); single-writer is fine for a single-user box. One honest gap we accept for now: if the read_run task itself crashes mid-run, the run is orphaned in Hermes — recovery (re-reading Hermes for the result) is manual until the Streams layer lands.

The client flow

Three steps, and the order of the first two matters:

1.  POST /sessions                     -> { session_id }    (create)
2.  GET  /sessions/{id}/events  (SSE)  -> stream opens       (subscribe — keep open)
3.  POST /sessions/{id}/messages       -> 202                (send)
        … replies arrive on the stream from step 2 …
4.  POST /sessions/{id}/messages       -> 202                (send again, same open stream)

Subscribe before you post

If you POST first and Hermes replies in the same instant, events can publish before the phone subscribed — and with ephemeral pub/sub they'd be missed until a reconnect-replay. Opening the stream first closes that race in the happy path.

One stream, many messages

The event stream is opened once when the chat screen loads, not per message. Every subsequent POST …/messages streams its replies back down that same already-open connection.

Reconnect = replay

On a dropped connection the app re-opens with Last-Event-ID; the API replays missed events from SQLite, then resumes live. Backend-agnostic — true for Hermes or gaca-agent.

This whole flow is identical whichever engine is behind the adapter — which is the proof the seam is in the right place. The Android app's interaction pattern never changes when we swap Hermes for our own loop.

What runs on the Pi

Processes (systemd units)

  • gaca-api — FastAPI; the adapter is an HTTP client to Hermes. (One worker fine; Redis allows more later.)
  • hermes gateway — the api_server adapter on :8642, API_SERVER_KEY set, its own ~/.hermes (pin a version — it's a fast-moving MIT repo).
  • redis — pub/sub transport.
  • sqlite — system of record (sessions, messages, events, audit). Embedded, so it's not a process at all — just a file the API opens; trivial and reproducible under Nix with no MongoDB-on-ARM packaging pain (the deciding factor), and it aligns us with Hermes, which already uses embedded SQLite for its own state.db.

Operational notes

  • Hermes is a sibling daemon, not in-process — "no separate GACA layer" means no translation service of ours, but Hermes itself is still its own service.
  • Cloudflare (Tunnel + Access) stays the outer gate in front of gaca-api only; Hermes is never exposed — it binds to localhost.
  • Deploy stays Nix + systemd, no Docker, per the Full GACA Plan.

Leak-point checklist — get these right now

The things that, if skipped, force a route/service/app change later (defeating the whole point):

Opaque session mapping

Store Hermes' session id as an opaque agent_ref field on the session doc that only the adapter reads — never a Hermes-named column. A future engine puts whatever it wants there.

Neutral event schema is the contract

Define GacaEvent in schemas/ first. The app and services depend on it, never on Hermes' shapes. The translator is the only thing that knows both.

Capabilities, not hardcoded features

Drive app features off GET /capabilities (the adapter reports its backend's support). Swapping engines changes the feature surface with no app code change.

Approval reserved in the contract

Put submit_approval in the port and the /approvals route in now, even if only the Hermes adapter wires it — so enabling it later isn't a contract change.

Audit from translated tool events

Translate Hermes' tool.started/completed/failed into audit entries. Caveat: Hermes streams tool args but not tool output (output is in state.db) — fetch outputs from /api/sessions/{id}/messages if you want them logged.

read_run lifecycle

The task must outlive the 202 (an app-scoped asyncio task, not tied to the request) and be cleaned up if the run hangs or the session closes. Nail this before writing tools.

Still open / to verify

To verify against a live Hermes

  • SSE event JSON field shapes — names are read from source; confirm the exact payload of each run.*/assistant.*/tool.* event before hard-coding the translator.
  • Does Hermes expose a memory HTTP API? If yes, the memory adapter calls it; if no, it reads memory_store.db on disk (accepted coupling, contained in the adapter).
  • Run re-attach / replay — can we reconnect to a run's SSE after a reader crash, or only read the final result from the session?

To decide at build time

  • Session-id mapping store: a column on the sessions row vs. a small mapping table.
  • How much of Hermes' tool.progress/commentary we surface vs. drop as noise.
  • Which Hermes model config the runs use; where its API_SERVER_KEY + model keys live (env/secrets).
  • Whether to expose memory endpoints at all in phase 1, or keep memory internal to runs.

Build order

The spine first
  1. Stand up Hermes with the api_server adapter on :8642; confirm POST /v1/runs + GET /v1/runs/{id}/events by hand (this also pins the event shapes).
  2. gaca-api: POST /sessions, GET /sessions/{id}/events (SSE over the Redis bus), POST /sessions/{id}/messages → 202, SQLite persistence, the bus.py publish/subscribe.
  3. The HermesAdapter: start_run + the read_run task that consumes Hermes' SSE, translates to GacaEvent, persists, and publishes.
  4. Point gaca-testui (React) at it and watch a message round-trip: type → 202 → Hermes runs → events stream back, audited.
  5. Then layer: audit from tool events, the MemoryBackend read, /capabilities, reconnect-replay, and the native app.
That round-trip — text → 202 → Hermes run → translated events stream back over Redis, persisted to SQLite, while the session stays responsive — is the whole spine. Owning the loop ourselves is then just a second adapter behind the same port.

Locked decisions

The constraints any work on the Hermes layer must honor. These extend the Full GACA Plan's locked decisions — where they overlap, these win for this phase.

Honor these
  1. Hermes is the agent backend, behind an adapter. The agent loop is adopted (Hermes Agent), reached as an HTTP client at localhost:8642 — never embedded in-process, never by reading its DB except inside the memory adapter as a documented fallback.
  2. Ports & adapters is the law. Routes and services depend only on the AgentBackend and MemoryBackend ports. All Hermes-specific code lives in agent/hermes/; grep -ri hermes outside that dir returns nothing.
  3. The adapter produces neutral events; the core sequences, persists, fans out, and audits. The Android app and services know only the GacaEvent schema, never Hermes' event shapes.
  4. A future gaca-agent is a second adapter. Switching engines is a config flip (AGENT_BACKEND) — no change to routers, services, schemas, or the app.
  5. Memory is handled in the agent layer behind MemoryBackend. Phase 1 the Hermes adapter reads Hermes' own memory (its API if present, else memory_store.db); gaca-memory slots in later behind the same port.
  6. Redis is pub/sub fan-out only, for now. The read_run task publishes events to session:{id}; the events handler subscribes and relays to the phone. No Streams/dispatch/inbox layer yet — Hermes owns run routing and lifecycle.
  7. SQLite is the durable record. Every event is persisted as it's published; Redis is ephemeral; reconnect replays from SQLite by Last-Event-ID.
  8. The client flow is create → subscribe → post. The event stream opens before the first message and is reused across messages; POST …/messages returns 202 and all output arrives on the stream.
  9. The read_run task outlives the 202. It is an app-scoped background task, not tied to the request, and is cleaned up on run end, hang, or session close.
  10. Session identity is mapped opaquely. Hermes' session id is stored as an opaque agent_ref; the core never interprets it.
  11. Hermes runs as a localhost-only sibling daemon under Nix + systemd, pinned to a version, never exposed through Cloudflare. Only gaca-api is reachable from the edge.

This is the near-term build plan: it keeps the Full GACA Plan's API and app, swaps the self-built loop for Hermes behind an adapter, and uses Redis pub/sub for event fan-out with SQLite as the record.
