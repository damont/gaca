05 · The Experiment

Odysseus on shire, reached through Cloudflare

The concrete plan you decided on: run Odysseus on your Raspberry Pi 5 shire, with Anthropic Opus as the agent brain (capped so it can't run up a bill) and your ChatGPT/Codex subscription doing the token-heavy coding via the Codex CLI. Reach it from your Android phone over Cloudflare, and let it deploy and drive your apps on a second Pi, piservices. Below: the architecture, what controls what, and step-by-step setup verified against the actual Odysseus repo, the Codex CLI docs, and Anthropic's spend-limit controls.

Host: shire (Pi 5) Brain: Anthropic Opus (API key, capped) Coding: Codex CLI (ChatGPT sub) Access: Cloudflare Tunnel + Access Apps host: piservices (Pi) Pi↔Pi: SSH to deploy · REST API to act UI: Odysseus PWA

The architecture

What controls what

Odysseus (on Opus) is the brain

The Odysseus FastAPI app on shire, running on Anthropic Opus, is the orchestrator. Its agent loop decides everything: when to think, run a bash command, SSH to piservices to deploy, call a piservices app's REST API as you, use search/memory — and crucially, when to hand a coding task to Codex. Opus does tool-calling and vision; it sees summaries, not giant diffs.

Codex does the coding, on your subscription

When the brain decides "this is a coding job," it shells out to the Codex CLI (codex exec), which authenticates with your ChatGPT/Codex subscription and runs as a full coding agent (its own tools + sandbox). The token-heavy work runs flat-rate, not on the metered Anthropic key — that's the cost win.

You only ever talk to Odysseus

Your phone hits odysseus.example.com → Cloudflare → the tunnel → Odysseus. Everything downstream (Anthropic, Codex, piservices, tools) is Odysseus acting on your behalf. piservices has no UI here; Odysseus reaches it.

Cloudflare is the doorway, not a component

Cloudflare does two jobs: terminate HTTPS (which also lets your phone's mic work) and enforce Access so only your email gets in. It holds no app logic. The tunnel is outbound from shire, so your home network exposes nothing.

Only the model is rented — and it's capped

Everything runs on your hardware except the two model providers. Opus is metered (pay-per-token) but hard-capped by an Anthropic workspace spend limit so a confused loop can't run up a bill; coding rides your flat subscription. Swap Opus for a local model later (per the Hardware page) and nothing else changes.

Two things to keep in mind Odysseus is AGPL-3.0, fast-moving, and its default branch is unstable — build from the main branch and re-check the README before pulling updates. And its bash/SSH tools are powerful and run as your admin user with no built-in approval gate — only you should have an account, and be deliberate about what you let it do to piservices.

Step-by-step setup

Replace example.com with your real Cloudflare domain throughout. Commands assume 64-bit Raspberry Pi OS and your user is david.

0 · Prerequisites

  • shire: Raspberry Pi 5 on 64-bit Pi OS (uname -m → aarch64), with Docker + Docker Compose. The official package (curl -fsSL https://get.docker.com | sh, then sudo usermod -aG docker $USER + re-login) is the smoothest. If you installed the snap instead, it works but is confined — see the snap note below.
  • A domain on Cloudflare (nameservers pointing to Cloudflare).
  • An Anthropic API key (sk-ant-…) for the agent brain — created inside a dedicated, spend-capped workspace (step 2).
  • An active ChatGPT Plus/Pro (Codex) subscription for coding, plus Node 18+ on shire to install the Codex CLI.
  • piservices reachable on the LAN (note its IP/hostname, e.g. piservices.local).
If Docker on shire is the snap Snap Docker is AppArmor-confined — works, with these gotchas:
  • Clone the repo under your home dir (~/odysseus) — snap Docker can only bind-mount paths under $HOME. Put it under /opt, /srv, or /mnt and the ./data volumes silently come up empty (you'd lose auth/settings/ssh keys). For an external SSD under /mnt: sudo snap connect docker:removable-media.
  • Manage the daemon via snap, not systemd: sudo snap restart docker, sudo snap logs docker (not systemctl). restart: unless-stopped still survives reboots.
  • Confirm the compose command: docker compose version; if the plugin's absent, use docker-compose (hyphen).
  • Data lives under /var/snap/docker/…; log-rotation config goes in /var/snap/docker/current/config/daemon.json, not /etc/docker/daemon.json.
  • Hitting empty-volume or permission weirdness? That's the confinement — sudo snap remove docker then the official install above is the clean fix. cloudflared and the Codex CLI are unaffected by how Docker was installed.

1 · Install Odysseus on shire

Use the main branch (the default dev branch is flagged unstable) and do the full build from source on the Pi. Since you're cloning main, you want the image built from exactly that source — building locally is the consistent choice (a prebuilt image would make cloning the source pointless). The first build compiles for a few minutes on a Pi 5; it's a one-time cost.

# clone the stable branch
git clone -b main https://github.com/pewdiepie-archdaemon/odysseus.git
cd odysseus

# create your env file
cp .env.example .env

Edit .env with at least these (everything else can stay default):

# (no model key in .env — add the Anthropic brain key in-app: Settings → providers, step 2)
AUTH_ENABLED=true
LOCALHOST_BYPASS=false
SECURE_COOKIES=true                        # you're serving HTTPS via Cloudflare
APP_BIND=127.0.0.1                         # keep loopback; the tunnel reaches it locally
APP_PORT=7000
ALLOWED_ORIGINS=https://odysseus.example.com
PUID=1000
PGID=1000

Build and start the full stack from the cloned source. The shipped docker-compose.yml already uses build: . — leave it as-is and pass --build so Compose compiles the image locally. Then grab your first-login password (printed once to the logs):

# full build from the main source, then run
docker compose up -d --build

# optional: include the heavier document tooling (PyMuPDF/Office, AGPL)
# docker compose build --build-arg INSTALL_OPTIONAL=true && docker compose up -d

docker compose logs odysseus | grep -i "Temporary password"
Sanity check On shire itself: curl -I http://127.0.0.1:7000 should respond. The compose stack also starts chromadb (:8100), searxng (:8080), and ntfy (:8091), all bound to loopback. Inference runs remotely (Opus + Codex are both cloud), so with vision/STT off, idle RAM on the Pi is roughly 1–2 GB — comfortable on an 8 GB Pi 5.

2 · The brain (Anthropic Opus) + the coding agent (Codex)

Two model providers, two different jobs. Opus is the brain — it does the tool-calling and vision that make Odysseus an agent. Codex is the coding worker — it runs on your flat subscription so the token-heavy coding doesn't hit the metered key. Why split this way: in Odysseus the in-app "ChatGPT Subscription" provider has no tool-calling and no vision (verified in the code), so the subscription can't be the brain — but the Codex CLI is a full coding agent on that same subscription. So the brain rents Anthropic; coding stays on what you already pay for.

Brain → Anthropic Opus (tools + vision)

In Odysseus, add Anthropic as a cloud endpoint in Settings → providers: base URL api.anthropic.com, paste your sk-ant-… key. Odysseus speaks the native Anthropic Messages API — tool-calling and image input both work (unlike the subscription path).

Models & pricing (per 1M tokens, input / output):

claude-opus-4-8$5 / $25default brain latest Opus
claude-opus-4-6$5 / $25the one you named — same price
claude-sonnet-4-6$3 / $15cheaper; route routine/utility here
claude-haiku-4-5$1 / $5cheapest; background tasks

Set Opus as the default model. Odysseus has per-role models (default / utility / task / research) — point utility/task at Sonnet or Haiku to cut spend. (Anthropic isn't in the README's provider list but is fully supported in code — add it via the Settings UI, not .env.)

Coding → Codex CLI (your subscription)

Install the Codex CLI on shire and sign it in with your ChatGPT subscription — then the brain shells out to it for coding.

# install (npm needs Node 18+) — or grab the arm64 binary
npm install -g @openai/codex
#   codex-aarch64-unknown-linux-musl.tar.gz also works on 64-bit Pi OS

# sign in with your ChatGPT subscription
codex login            # browser OAuth; on a headless Pi use the
                       # device-code login, or copy ~/.codex/auth.json
                       # from a machine you already signed in on

The brain invokes it non-interactively and captures the diff:

cd /path/to/repo
codex exec --json --sandbox workspace-write \
  "Implement X, run tests, leave changes uncommitted" \
  -o /tmp/codex-summary.txt
git -C /path/to/repo diff > /tmp/codex.diff
The cost cap — your "runaway bill" guardrail This is the fix for "what if it gets confused and runs up my Opus bill." Anthropic lets you hard-stop spend:
  1. In the Anthropic Console, create a dedicated Workspace for Odysseus (you can't set a limit on the default workspace, so make a new one).
  2. Set that workspace's spend limit to a hard monthly ceiling — e.g. $15. Past it, the API rejects requests until the next calendar month. It's a stop, not a throttle.
  3. Create the API key inside that workspace (keys are bound to their workspace and inherit its cap) and use that key in Odysseus.
  4. Add a threshold email alert (e.g. at 50–80%) so you hear about it early, and set an org-level spend limit as a backstop.
Because the brain only sees summaries and hands coding to Codex, real orchestration is cents per task — a $15 cap is generous headroom and an absolute ceiling. Prompt caching (Odysseus marks the Anthropic tool/context blocks ephemeral) cuts it further; cached reads don't even count against your rate limit.
One honest caveat on Codex-via-subscription OpenAI positions "Sign in with ChatGPT" as the interactive developer path and steers unattended/automated use toward API keys. Driving Codex headlessly from the Opus brain works and is fine when you're in the loop approving, but it's a gray area for the subscription ToS and could get throttled if hammered. If it ever does, the drop-in fix is to point the Codex CLI at an OPENAI_API_KEY instead (pay-per-token) — or let Opus do the coding directly (costs more on the capped key). Also tell the agent (via a skill / system note) to delegate coding to codex exec rather than editing files itself with Opus — otherwise the expensive part lands back on the metered key.

3 · Create the Cloudflare Tunnel on shire

The tunnel is an outbound connection from shire to Cloudflare — no port forwarding, nothing exposed on your router.

# install cloudflared (Cloudflare apt repo — auto-updates)
sudo mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' | sudo tee /etc/apt/sources.list.d/cloudflared.list
sudo apt-get update && sudo apt-get install -y cloudflared

# authenticate (opens a browser link; pick your domain) and create the tunnel
cloudflared tunnel login
cloudflared tunnel create odysseus       # prints a Tunnel UUID + writes ~/.cloudflared/.json

Create ~/.cloudflared/config.yml (use the UUID, not the name):

tunnel: <TUNNEL-UUID>
credentials-file: /home/david/.cloudflared/<TUNNEL-UUID>.json

ingress:
  - hostname: odysseus.example.com    # BARE domain — no https:// (a scheme here = "hostname cannot contain a port")
    service: http://localhost:7000    # service DOES keep its scheme
  - service: http_status:404          # required catch-all, must be last
# validate, create the DNS record, then run as a service
cloudflared tunnel ingress validate
cloudflared tunnel route dns odysseus odysseus.example.com

# install as systemd (service runs as root → keep config + creds in /etc/cloudflared)
sudo mkdir -p /etc/cloudflared
sudo cp ~/.cloudflared/config.yml /etc/cloudflared/config.yml
sudo cp ~/.cloudflared/<TUNNEL-UUID>.json /etc/cloudflared/<TUNNEL-UUID>.json
# edit credentials-file path in /etc/cloudflared/config.yml to the /etc copy
sudo cloudflared service install
sudo systemctl enable --now cloudflared
journalctl -u cloudflared -f            # watch it connect

4 · Lock it to just you with Cloudflare Access

Don't skip this A tunnel hostname is publicly reachable — the tunnel hides your IP but does not authenticate anyone. Without Access, whoever learns odysseus.example.com reaches your Odysseus login directly. Access enforces your identity at Cloudflare's edge before traffic ever reaches shire.

In the Cloudflare dashboard → Zero Trust (pick a team name the first time):

  1. Access → Applications → Add an application → Self-hosted.
  2. Application domain: odysseus.example.com.
  3. Add an Access policy: Action = Allow, Rule = Include → Emails → david.monts@gmail.com.
  4. Identity: enable One-time PIN (built-in, emails you a code) and/or add Google for one-tap login.
  5. Save. Now the hostname shows a Cloudflare login; only your email passes, then you hit the Odysseus login.

Zero Trust Free covers up to 50 users — you're free. You now have two auth layers (Cloudflare Access + Odysseus login), which is exactly what you want for something with shell access.

7 · Connect Odysseus → piservices — two distinct modes

Your apps on piservices are newbuild apps (FastAPI + React + Docker), and they're built for exactly this. Crucially, they already define an agent access contract (newbuild Phase 10), so Odysseus doesn't get raw database or shell access to your data — it acts as you through the same REST API your frontend uses. Keep the two jobs separate:

Mode A — SSH = run / update the apps

Operations on the machine: pull the latest code, rebuild, restart, read logs. This is the deploy/ops plane.

Mode B — REST API = interact as your user

Operations on the data: list/create/update resources inside an app, exactly as if you clicked around the UI. This is the user plane, authenticated with a per-app agent JWT.

Mode A · SSH for deploy & updates

Odysseus has a built-in remote-server (SSH) feature — cleaner than ad-hoc shell. It generates an SSH key (persisted in ./data/ssh, mounted into the container) that you authorize once on piservices.

  1. In Odysseus: Cookbook → Settings → Servers → add a server (name piservices, host piservices.local or its LAN IP, your SSH user). It shows you its generated public key.
  2. On piservices: add that key to ~/.ssh/authorized_keys.
  3. Now Odysseus can run your standard newbuild deploy steps on piservices — e.g. cd ~/apps/<app> && git pull && docker compose up -d --build, trigger the auto-deploy script, restart a container, or tail logs. This is the only thing SSH is for here.

Where do the code changes come from? The Codex CLI (step 2) edits a checkout of the app's repo; the brain then either pushes (your apps auto-deploy on push to main) or runs the deploy steps above over SSH. Codex writes the code, SSH ships it — and the metered Opus key is barely touched by either.

Keep modes from bleeding together Resist the temptation to have the agent ssh … mongosh or poke the database directly to "interact" with an app. Your apps deliberately route all cross-app communication through REST (newbuild rule: apps never touch each other's DBs). Treat Odysseus as just another API client and you inherit that app's validation, auth, and user-scoping for free.

Mode B · REST APIs to act as you

Each newbuild app exposes a long-lived Bearer JWT agent token and a self-describing API. Per app, once:

  1. Mint a token. Open the app (e.g. https://invest.example.com) → profile page → Agent tokens → Generate → pick 365 days → copy the JWT. (It's scoped to your user, same as any session.)
  2. Grab the setup guide. Same section has a Download skill button → it gives you <app>-agent.md (what the app is, its data model, the auth rule, and the discovery URLs). This file is written to onboard any agent — Odysseus included.
  3. Note the base URL + discovery. Endpoints are not hard-coded — the agent reads <base>/api/openapi.json (Swagger UI at <base>/api/agent) to learn the surface.

Then wire each app into Odysseus. Two ways, start with the first:

Option 1 — skill + token (recommended start)

  • Add <app>-agent.md to Odysseus as a skill (it's already a SKILL-style bundle) or as memory/context.
  • Store the base URL + JWT in Odysseus's secrets/settings (not a committed file).
  • The agent calls the API with its bash tool (curl) following the guide: Authorization: Bearer <jwt> on every request, discover via /api/openapi.json.

Lowest effort, and exactly the workflow your apps were designed to hand an agent.

Option 2 — OpenAPI → MCP (cleaner tools)

  • Run an OpenAPI-to-MCP bridge pointed at <base>/api/openapi.json, injecting the Authorization: Bearer header.
  • Add it in Odysseus: Settings → MCP (custom server, stdio/http, admin-only).
  • Now each endpoint is a first-class typed tool instead of curl-via-bash.

More setup, better tool-calling. Worth it once an app is a daily driver.

Which base URL — Cloudflare hostname or LAN?

These apps authenticate with their own JWT, not Cloudflare Access — so Odysseus needs no service token, just the Bearer JWT. Pick the base URL:

  • Public hostname (https://invest.example.com) — simplest; matches what the token + <app>-agent.md assume; works the same whether you're home or not.
  • LAN (http://piservices.local:<app-port>) — a latency optimization that keeps Pi-to-Pi traffic off the internet and dodges the 100 MB / 524 edge limits. Same JWT works. Use this if you do heavy/bulk calls.

Behavior rules to give Odysseus (straight from your apps' guide)

RuleWhy it's in the contract
Read /api/openapi.json first; never assume endpoint pathsEndpoints change between releases — the schema is the source of truth.
Stay in your user; one Bearer header per requestEvery resource is user-scoped; that token is your identity.
Prefer endpoints marked bulk / upsert / idempotentSafe to re-run — better for backfills than many single creates.

Your newbuild apps use app-level JWT auth (not Access), so you normally won't need this.

Where this can grow This experiment rents a capped Opus brain, runs coding on your Codex subscription, deploys piservices apps over SSH, and acts on them via their REST APIs. Upgrades that drop in without changing the shape: (1) swap the Opus brain for a local model — see Hardware & Models — and your API bill goes to $0 (a provider change in Settings); (2) graduate Mode B from "skill + curl" to a per-app OpenAPI→MCP bridge so every endpoint is a first-class tool. If you later outgrow Odysseus's "you live inside its agent" model, the GACA Plan is your path to a core you fully own — and your apps' agent contract carries over unchanged.
