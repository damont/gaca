How the agent actually uses it — a direct tool call, no queue

The simplest setup, and the one chosen: install codex + git + gh directly on shire, and run the GACA backend itself on the host (a systemd service as your user). Then a tool call directly runs your Codex — no separate worker, no queue, no process watching anything. No sandbox to start. The agent reaches it through two pieces — a tool and a skill:

The tool (the hands)

A function in the loop that executes: run_coding_task(repo, instructions) does await asyncio.create_subprocess_exec("codex", "exec", "--sandbox", "workspace-write", …) and returns the diff. Because the backend runs on the host as you, it uses your Codex login directly. It's async under the hood (a long codex run doesn't block other requests), but to the model it's just one tool call. Without a tool, the model can talk about codex but can't run it.

The skill (the how/when)

A SKILL.md the model loads when relevant: "to make a code change — find the repo, call the coding tool with clear instructions, review the diff, push a branch, open a PR." Your newbuild apps already generate exactly this kind of skill file. The skill is knowledge; the tool is execution — you give it both.

GitHub follows the same shape: gh auth login once with a fine-grained PAT, the skill describes the PR workflow, and the tool (or the official GitHub MCP server) does clone / push / open-PR.

Two cheap safety nets to keep, sandbox or not Because GACA reads your email and is reachable over the internet, it's prompt-injectable — so even running wide-open: (1) make the GitHub token fine-grained, scoped to just the repos it needs (not your whole account), and (2) put the approval gate on push/PR. Worst case then is "it touched two repos you authorized," not "it had your entire GitHub." Everything else can run unrestricted. The sandbox stays a clean later upgrade — the worker just launches codex inside a container instead of on the host, behind the same tool: a deploy change, not a rewrite.

8 · The trust layer OWN

Small to build, and the entire reason you left Odysseus. Four pieces, all yours:

Permission policy

One place that knows "Gmail = read-only, Calendar = write-with-approval, these repos only." The loop asks; the policy enforces.

Approval gate

Risky/irreversible actions pause and push a confirm to your phone. The thing Odysseus has no concept of.

Audit log

Every tool call + decision, one JSON line, queryable. So you can always answer "what did it do, and why" — no black box.

Scheduler

Cron-style proactive jobs (morning brief, watch a repo) — APScheduler or systemd timers, no Redis/Celery on a Pi.

A "dry-run" mode

Show intended actions without doing them — invaluable while you're learning to trust it.

Readable tool list

Because you wrote it, the agent's tools are exactly what config says — no confabulated "I have no shell" mysteries.

9 · Subagents OWN

A subagent is just another run of your agent loop — a fresh context, a scoped system prompt, and a subset of tools — that the main agent spawns to do a focused job and then collects the result from. Pydantic AI supports this directly (agent delegation / "agents as tools"), so a subagent is simply a tool that happens to run another agent.run().

Why you want them

  • Keep the main context lean. The subagent does the messy work (reads 40 emails, crawls a repo) and returns a short summary — the parent never sees the raw mess. This is the biggest reason, beyond parallelism.
  • Parallel fan-out. Spawn three at once — check email, check calendar, scan a repo — and merge the answers.
  • Specialization. A research subagent with web tools; an email-triage subagent with read-only Gmail; the coding job (which for you is Codex). Each gets only the tools it needs.

How it works in GACA

  • A spawn_subagent(task, role, tools, model) capability — each call is a new agent.run() with its own prompt, tool subset, and clean context.
  • Runs in the host backend as async tasks — parallel/long subagent work doesn't block other requests.
  • Subagent tool calls go through the same policy / approval / audit — a subagent is not a back door around the trust layer.
Two things to get right Cost — every subagent burns tokens on your metered brain, so default subagents to a cheaper model (Sonnet/Haiku via the gateway's per-role routing) and reserve Opus for orchestration; the spend cap still backstops you. Depth — cap how deep subagents can spawn subagents (1–2 levels) so a confused agent can't fork-bomb itself. Note the Codex coding agent is a subprocess, not a GACA subagent — different mechanism, same idea: delegate a focused job, collect the result.

10 · Scheduled jobs OWN

So far GACA is reactive — you talk, it answers. Scheduled jobs make it proactive: an agent run triggered by time instead of by you. "Brief me at 7am," "watch this repo for new issues," "check email hourly and ping me if something's urgent." A scheduled job is just an agent run with a preset prompt, fired on a cron/interval.

How it works in GACA

  • Runs inside the host backend process: APScheduler with a job store in Mongo (or systemd timers). Each fire = an agent.run() — same process, no separate watcher.
  • Jobs are defined in config or created by the agent itself via a schedule_job tool — so you can just say "every morning, brief me" and it sets it up.
  • Results are pushed to your phone (ntfy / web push) or stored to read later — you're not in the chat when it runs.

The tension to decide

A scheduled job can't wait forever for a phone tap, so decide per job type:

  • Read-only jobs (briefings, watches) run freely — nothing to approve.
  • Write jobs either run under a standing pre-authorization ("auto-label email = ok"), prepare a draft and ask, or pause and notify you to approve next time you're around.
Keep them cheap Scheduled runs burn tokens unattended — scope them tightly, route them to a cheaper model (Haiku/Sonnet), and lean on the capped Anthropic spend (this is exactly what it's for). Also guard against overlap: don't start the next run while the last is still going.

LangChain/LangGraph vs Pydantic AI

First, a naming clarification: "LangChain" in 2026 means LangChain 1.0 + LangGraph. The old classic-LangChain agent (AgentExecutor, LCEL chains) is deprecated — the agent story moved to LangGraph, and the prebuilt entry point is create_agent. So the real comparison is LangGraph vs Pydantic AI. (Side note: Pydantic AI is by Pydantic Services Inc. — Samuel Colvin's team, makers of the Pydantic library that the OpenAI/Anthropic/Google SDKs all use — not by Anthropic.)

Your direct questions, answered:

  • Do they have their own agent loops? Yes, both. LangGraph runs the loop via create_agent on a graph runtime; Pydantic AI runs it via agent.run(). Neither makes you hand-write the model→tool→result→repeat cycle.
  • Research agents? LangChain yes, prebuilt — deepagents and "Open Deep Research" are batteries-included deep-research harnesses (planning, sub-agents, persistent memory). Pydantic AI: mostly primitives — there's a newer official pydantic-ai-harness and a third-party pydantic-deepagents, but they're younger/less battle-tested. So if "prebuilt deep research out of the box" matters, that's a real LangChain edge.
  • Various models? Both support OpenAI, Anthropic, Gemini, Ollama/local, and ~dozens more; both swap providers by changing one model object/string; both are MCP clients.
  • Is LangChain "more advanced"? Fair — but read it as "more capable and more complex," not "strictly better." It's ahead on breadth: bigger ecosystem, built-in durable checkpointing (resume after a crash, time-travel debugging), and the prebuilt research/deep-agent harnesses. The flip side is that breadth: more concepts, heavier dependencies, a recent history of churn, and gravitational pull toward the paid LangSmith SaaS.

How the agent actually calls tools

This is the part with no magic — and once it clicks, the whole system makes sense. The model cannot call anything. It can only produce text. The trick is that you let it produce a structured request to call a tool, and then your code does the actual work and hands the result back. The model decides what and with what arguments; your harness decides how it's really done and whether it's allowed.

The loop, concretely:

  1. You advertise tools as JSON schemas. Each tool = a name, a description, and an input schema. You send this list with every model request. Example: {"name":"create_calendar_event","description":"Add an event to David's calendar","input_schema":{...start, end, title...}}.
  2. The model emits a tool-call intent. Mid-response it returns a structured block: "call create_calendar_event with {title:'Dentist', start:'…'}" and the API stops (Anthropic: stop_reason: "tool_use"; OpenAI: a tool_calls array). No action has happened yet — it's just the model saying what it wants.
  3. Your harness dispatches it. This is the layer you own. You look up the tool name in your registry and run whatever that tool actually is — and this is the answer to "how does it call other parts of the system": the name maps to a mechanism.
  4. Policy/approval gate fires here, before dispatch. "Is this tool allowed? Does it need a phone tap first?" The model never bypasses this because the model isn't doing the calling — you are.
  5. You feed the result back as a tool_result and call the model again. It reads the result and either calls another tool or writes the final answer (stop_reason: "end_turn"). Repeat until done.

The dispatch table is the heart of it — one tool name, many possible mechanisms:

Tool the model namesWhat your harness actually doesMechanism
get_current_timeCall a local Python functionin-process function
search_email / create_calendar_eventCall the Google Workspace MCP serverMCP client → MCP server
run_coding_taskcd repo && codex exec "…", capture the diffsubprocess (Codex CLI)
add_to_invest_watchlistHTTP POST https://invest…/api/… with your Bearer JWTHTTP → your app's REST API
deploy_appssh piservices "cd ~/apps/… && git pull && …"SSH to the other Pi

So "the agent calling other parts of the system" is really your dispatch function routing a named tool to the right mechanism — a function, an MCP server, a subprocess, an HTTP call to your apps, an SSH command. The model stays blissfully ignorant of all of it; it just knows tool names and argument shapes.

What the framework does vs what you do

A framework like Pydantic AI automates steps 1–2 and 5 (advertising schemas from your function signatures, parsing the model's tool-call, looping) and dispatch for in-process functions and MCP. You still write the tool functions, the registry, and — importantly — the policy/approval gate and the audit log around dispatch. That's the seam where "owning the loop" actually matters: the framework runs the cycle, but you decide what's allowed, what pauses for approval, and what gets logged. A rough shape:

async def dispatch(call):                  # YOUR code, the seam you own
    if not policy.allows(call.name):       # permission policy
        return tool_error("not permitted")
    if policy.needs_approval(call.name):   # approval gate → phone tap
        if not await approvals.confirm(call):
            return tool_error("denied by user")
    audit.record("tool_call", name=call.name, args=call.input)
    result = await registry[call.name](call.input)   # fn / MCP / subprocess / HTTP / SSH
    audit.record("tool_result", name=call.name, ok=True)
    return result

The model emits call; everything after is yours. That single function is most of the "trust layer."

"How does an API in a container run a shell / Codex / SSH?"

The thing to flip in your head: a Docker container is a Linux machine. It has its own filesystem, its own processes, and its own shell. When your FastAPI code does subprocess.run("git …"), that command runs inside the container, in the container's userland — not on the host. So "the API has shell access" really means "the API can run processes inside its own container." That isolation is a feature: the agent's shell is boxed in, away from the host.

Two consequences that answer the confusion:

  • It can only run what's in the image. A container can't run git, ssh, or codex unless those binaries are installed in its image — it can't reach a copy installed on the host.
  • It can't be your host user. A container runs as root (or a container user), not as david, and it can't see your home dir — so it doesn't have your ~/.codex login, ~/.config/gh, ~/.gitconfig, or ~/.ssh unless you explicitly hand them over.
"Can the agent in Docker run my host CLIs as me?" By default, no. A container can't execute a binary installed on the host, and it isn't your user, so it has none of your CLI logins. Two clean ways to get what you want:
  1. Run the GACA backend on the host as your user (simplest — what you chose). Don't containerize the agent. Run the whole backend (API + agent loop + scheduler) directly on shire as david (a systemd service), and a run_coding_task tool just subprocess-runs your Codex directly — it natively has your codex login, gh auth, git config, and SSH keys. No queue, no mounting, no UID juggling. The web PWA can still be a container.
  2. Or keep the agent in a container and hand it your credentials. Install codex/git/gh in the image and bind-mount your credential dirs (~/.codex, ~/.config/gh, ~/.gitconfig, ~/.ssh) in, running the container as your UID. The tool call still works directly — it's just the container's CLI using your auth. Works, but you've put your real credentials inside the container and have to match file ownership.
For your "install it on the box and use it" instinct, option 1 is the answer: the backend isn't in Docker, so a tool call running the CLI as you is just… true. (The queue-and-worker idea is gone — it only existed to bridge an in-container agent to a host CLI, which we no longer have.)

The other two needs are pure networking and don't care about any of this:

Reach Mongo

The host backend → just localhost:27017; a container → mongodb://host.docker.internal:27017. Either way, a normal connection.

SSH piservices

The ssh client + your key + a LAN route — an outbound connection. From the host backend it's literally ssh piservices as you.

Memory: short-term vs long-term, and why embeddings

The thing to internalize first: the model is stateless. It remembers nothing between API calls. Every "memory" it appears to have is just text you chose to put back into the request. So "memory" is entirely your job, and it splits into two very different problems.

Short-term (working) memory

The messages you send this turn: the system prompt, the recent conversation turns, and the current tool results. It's not stored specially — it is the request. You manage it by deciding how much recent history to include.

The catch: context windows are big but finite, and stuffing everything is slow, costly, and dilutes the model's attention. So when a conversation gets long, you summarize older turns into a running recap ("compaction") and keep only the recent verbatim turns + the recap. Anthropic/OpenAI even offer server-side compaction, but you can also just do it yourself.

Storage: the messages array in the request, plus a conversations collection in MongoDB so a session survives an app restart.

Long-term memory

Anything that must outlive the conversation and the context window: facts about you ("David's timezone is Central"), preferences ("terse replies"), decisions, and distilled summaries of past conversations. Stored in a database, and only the relevant bits are pulled back into context per turn — you never load all of it.

Two flavors:

  • Episodic — the log of what happened (your conversation history + audit log).
  • Semantic — distilled, durable facts/notes you want to recall later.

Storage: a MongoDB notes/facts collection; add vectors (next section) when you want meaning-based recall.

Why you'd need embeddings (and when you don't)

Long-term memory is only useful if you can find the right thing at the right moment. That's a search problem, and you have two options:

  • Keyword / SQL search. "Find notes containing 'dentist'." Great for exact matches and tags. Fails the moment the wording differs — a stored note "tooth doctor on the 14th" won't match a query about "my dentist appointment."
  • Semantic search via embeddings. An embedding turns a piece of text into a vector — a long list of numbers that captures its meaning. Texts with similar meaning land near each other in that number-space. So you embed the user's current request, find the stored notes whose vectors are closest, and you retrieve by meaning, not spelling — "tooth doctor" matches "dentist." That's the entire reason embeddings exist in this context: meaning-based recall over a growing pile of memories.
Do you need them? Not to start. If your memory is small or you mostly need "the last N turns + a few exact-match facts," a plain Mongo query (including its text index) is enough — skip embeddings entirely. You want embeddings once you've accumulated lots of notes and want the agent to surface what's relevant to this moment regardless of phrasing. The honest path: ship with recent-history + a notes collection, add vector recall when the notes pile up and keyword search starts missing things.
The Anthropic embeddings gotcha (again) Embeddings are a separate model from your chat brain, and Anthropic doesn't offer one. So even with Claude as your brain, vectors come from elsewhere: a local embedder (fastembed — ONNX, free, runs on the Pi, keeps your memories private) or OpenAI embeddings (text-embedding-3-small, cheap, per-token, leaves your machine). For a personal assistant, the local embedder is the better default — it's free and nothing about your memories leaves shire.

Where do the vectors live? "Since we use Mongo for everything…"

Good instinct — reuse Mongo. The nuance is only about the vector index, and at your scale it barely matters:

OptionFit for a single-user Pi
Brute-force in Mongo — store embeddings as arrays, compute cosine similarity in an aggregation pipeline, sort, limit start hereFor hundreds–low-thousands of notes this is milliseconds, needs zero new infrastructure, and keeps one store + one backup. The right default.
sqlite-vec sidecar — Mongo stays system-of-record for documents; a tiny SQLite file holds the vectors with a real KNN indexAdd this only if the store grows past ~10k notes or brute-force latency bugs you. Pure-C, ARM64, no daemon — but it's a second store to keep in sync.
MongoDB native vector search (the mongot search process)Skip on the Pi. It's a JVM/Lucene service still in public preview (not for production), wants dedicated hardware + multiple GB of heap, and has no confirmed ARM64 support. Overkill for a personal memory store on a shared Pi.

So: yes, keep everything in your existing Mongo — documents and brute-forced vectors — and reach for a sqlite-vec sidecar only if it ever outgrows that. All behind the Memory port, so the swap is an adapter, not a rewrite.

The practical GACA memory recipe

Per turn, assemble the context as: system prompt + last N conversation turns (short-term) + a running summary of older turns + top-K long-term notes retrieved for this query. After a conversation, decide what's worth keeping — either by simple rules or a cheap LLM call ("extract any durable facts/preferences") — and write those to the Mongo notes collection (with an embedding once you've turned vectors on). Start with everything except the embeddings; turn on fastembed + brute-force cosine in Mongo (or a sqlite-vec sidecar) behind your Memory port the day keyword recall isn't enough. If you'd rather not hand-write the "what's worth remembering + retrieve relevant" logic at all, that's exactly what Mem0 does — slot it behind the same port later.

One monorepo

For a solo builder, a single repo wins — atomic changes across api + web + core, one deploy. Mirrors your newbuild layout plus the agent bits:

gaca/
  apps/
    api/      # FastAPI: auth, intake, SSE, approvals
    web/      # React PWA
  core/       # the agent loop (yours)
  ports/      # ModelGateway, Tool, Memory,
              #   CodingAgent, Sandbox (interfaces)
  adapters/   # pydantic-ai/litellm, mcp, codex/aider,
              #   sqlite-vec+fastembed, bubblewrap
  integrations/mcp/   # github, google, your-apps
  config/     # policy.yaml, gateway, mcp
  deploy/     # compose, systemd, cloudflare notes

What runs on shire — separate containers

One compose file, each piece its own container (your newbuild pattern):

  • gaca-backend — one host service (systemd + uv, as your user): FastAPI + the agent loop + the scheduler + subagents. Runs on the host so tool calls reach your installed codex/gh/git/ssh directly — no queue, no separate worker.
  • web (container) — the built PWA behind nginx (static; happy in a container).
  • mcp servers — subprocesses the backend spawns, or small containers.
  • MongoDB — your existing host instance (its own DB), reached at localhost:27017.
  • Later: a litellm proxy; and the coding part can move into a sandbox container if you ever want isolation.

MongoDB stays on the host (your existing shared instance, GACA gets its own DB) — the containers reach it at mongodb://host.docker.internal:27017, exactly like your newbuild apps. Cloudflare reused — repoint a tunnel at the web/api port.

"Do I really want it all in one repo?" — yes, but separate the processes

The thing tripping you up is conflating one repo with one running process. They're different decisions:

One repo (recommended)

The PWA, the API, and the agent core are one tightly-coupled product: the PWA codes against your API; the API hosts the loop. A change usually touches more than one of them at once (add a feature → new endpoint + new UI + maybe a new tool). A monorepo means one atomic commit/PR, one CI, one deploy, one place to reason. For a solo builder, splitting them creates version skew (API and PWA drift apart), cross-repo PRs, and triple the CI — overhead with no payoff.

Note this is the opposite of your newbuild apps, which each get their own repo — because each of those is an independent product. GACA's web+API+core are one product, so one repo.

Multiple processes (from that one repo)

"One repo" does not mean one process. From the same repo you build and run several:

  • API process — FastAPI; the agent loop runs inside it (it's a module/library, not a separate service).
  • Web — the built PWA, served by nginx (its own container, like newbuild).
  • Scheduler/worker — a separate process for proactive cron jobs and long-running coding runs, so they don't block the API.
  • Coding agent — a subprocess (Codex) the worker spawns in a sandbox/worktree.
  • MCP servers — separate subprocesses the API talks to.

All defined and versioned together; deployed as a few containers via one compose file — exactly how newbuild ships a frontend + api + worker from one repo.

When to split a repo out later Extract a piece into its own repo only when it earns independence: an MCP server you reuse across projects, a worker that needs to scale or deploy separately, or if you ever want to open-source just the PWA. Until one of those is true, one repo is less friction. The ports/adapters boundary means extracting later is a clean lift, not a rewrite.

Suggested first milestone (crawl)

Phase 1 — a useful assistant in a weekend FastAPI + a thin agent loop over Pydantic AI (Anthropic or OpenAI by config) + JWT auth + your React PWA over Cloudflare + the audit log from day one + one MCP server (Google Workspace: Gmail read, Calendar write). No coding agent, no memory yet. Outcome: you talk to GACA from your phone, it reads your email and adds calendar events — and you can see every action it took. Then Phase 2 adds the run_coding_task tool (a direct codex exec call) + a skill + the approval gate; Phase 3 adds memory, subagents, and the scheduler (proactive briefings/watches pushed to your phone). The backend runs on the host throughout, so the coding tool call is direct.
