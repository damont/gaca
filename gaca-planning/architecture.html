Your diagram, with the safety & swap plumbing added

Same bones as your sketch. I've added the five things that turn a demo into something you can trust on a server you own: a model gateway, an auth/secrets layer, a sandbox boundary around subagents, an approval gate for write actions, and a scheduler + audit log.

Superseded in places This is the reference/principles page. The GACA Plan is canonical and updates three things shown below: the agent calls tools directly (the API publishes the catalog, it doesn't execute), memory is its own system (gaca-memory), and there's no Docker (Nix flake + systemd; isolation via bubblewrap, not containers). The safety concepts here — gateway, auth, sandbox, approval, audit — still apply.

Walking the request

  1. You speak/type/snap a photo in the native Android app. It reaches the Pi through Cloudflare (Tunnel + Access), which only lets your verified email through — no port is ever exposed to the internet.
  2. The API layer authenticates the call (single-user API key or short JWT), transcribes audio, and hands the request to the loop.
  3. The agent loop pulls relevant memory, may load a skill, and decides on a tool or a subagent. Model calls go through the LiteLLM gateway — local model or provider, its choice or your config.
  4. Read actions (search email, list events) run straight through MCP. Write actions (create calendar event, push to GitHub) hit the approval gate — you get a notification and tap to confirm.
  5. Coding/other subagents run inside the sandbox: bubblewrap + an ephemeral git worktree/container, network egress restricted, torn down after.
  6. Every tool call and decision lands in the audit log, so you can always see what your agent did and why.

The five additions, justified

1 · Model gateway (LiteLLM)

Your draft has "local LLM or provider" as one box. In practice you want a thin proxy in front so switching is a one-line config change — and you get automatic fallback (try local, fail over to provider), spend tracking, and one endpoint everything points at. Runs fine on the Pi. Details →

2 · Auth + secrets

Even behind Cloudflare Access, the API keeps its own app-layer auth so a stolen device session can't drive your agent. Single-user: Cloudflare Access (email allow-list) as the outer gate, plus a static API key or short-lived JWT at the API. Plus a real home for OAuth tokens and provider keys (env/secret file, never in code).

3 · Sandbox boundary

Subagents and the coding agent run model-generated code. Plain Docker shares the host kernel and isn't enough for untrusted code. Mirror Anthropic's own approach: bubblewrap + network proxy, each task in an ephemeral container/worktree, non-root, egress allow-list. (gVisor if your Pi kernel supports it.)

4 · Approval gate

You deliberately scoped email read-only but calendar and GitHub get writes. That asymmetry is exactly where a human-in-the-loop checkpoint belongs: risky/irreversible actions pause and push a confirm to your phone. Cheap to build, huge for trust.

5 · Scheduler + audit log

Your draft is purely reactive. A cron loop lets GACA act proactively — morning briefing, watch a repo, run a recurring job (your openclaw-style jobs). The audit log is what makes an agent you own trustworthy: a complete, queryable record of every action.

+ Permission policy on the tool router

One place that knows "Gmail = read-only, Calendar = write-with-approval, GitHub = these repos only, rate-limit X." The loop asks the router; the router enforces. Keeps scope decisions out of prompt-engineering and in code you can audit.

The integration surface (MCP)

Every external connection is an MCP server using your own OAuth client with the narrowest scopes. This is the cleanest way to satisfy "read-only email, write calendar, GitHub access."

Reaching it from your phone, securely

Remote access: Cloudflare

The whole stack is fronted by Cloudflare (which you already use for everything). A Cloudflare Tunnel connects out from the Pi, so no port is ever exposed and there's no inbound firewall hole; Cloudflare Access sits in front with an email allow-list so only your identity reaches gaca-api. You get TLS, a stable hostname, and identity-based auth for free.

Defense in depth: keep app-layer auth on the API even behind Cloudflare Access — the email gate is the outer layer, the API key/JWT is the inner one.

Android client: native app decision updated

The current plan builds a native Android app (gaca-android, Kotlin + Jetpack Compose) talking to gaca-api through Cloudflare — text + audio capture + image/file attachments with first-class mic, share-sheet, and notification access. (The earlier PWA / Open WebUI recommendation is superseded; see the GACA Plan.)

A PWA over Open WebUI remains the fastest way to prototype the endpoint before the native client lands.

Design principle Make the model swappable, the tools scoped, the subagents sandboxed, the writes approved, and the actions logged. Everything else is detail you can change later without touching the core.
