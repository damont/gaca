Standing Hermes up by hand

The Hermes Plan says adopt the engine. This page is the record of actually doing that — and of a deliberate choice: take the most minimal initial setup Hermes offers, then turn every capability on manually. The point isn't speed. Every switch flipped by hand here is a switch the HermesAdapter will eventually have to flip programmatically, because ADR 0001 puts model and provider config at runtime, through the API. You cannot automate a setup you have never performed.

State dir: ~/.hermes Gateway: 127.0.0.1:8642 Auth: ChatGPT subscription (OAuth) Model: gpt-5.6-sol Web backend: tavily GitHub: PAT via gh CLI Memory: Hermes built-in Front end: Telegram (temporary) Dashboard: 127.0.0.1:9119 Google: read-only via skill Apps: self-describing + agent tokens Build skill: FastAPI · React · Docker Reach: SSH → piservices Pi stack: nginx · docker · cloudflared · gh Host: base Ubuntu Desktop Posture: minimal-on-purpose
Why the minimal path was chosen on purpose A generous first-run wizard is exactly the wrong thing for this project. If the installer configures auth, web search, image gen, and platform integrations for you, then you never learn where any of that state lives — and the adapter we have to write is precisely the thing that must write that state on a user's behalf. So: take the smallest setup that boots, then add capabilities one at a time and watch what changes on disk. Every manual step below becomes a line item in the adapter's first-time-setup routine — and, as the last section shows, one of them has already graduated from a hand-typed command into the launcher.

The capabilities turned on so far

Booting Hermes gets you a gateway. It does not get you a useful agent. Four acts of access were needed first, and — this is the finding that keeps recurring — each one lands its credential in a different place. (Before any of them, the machine itself needed work: see Step 0.)

1 · A model to think with

OAuth into a ChatGPT subscription so Hermes can drive gpt-5.6-sol. Without a provider credential the gateway starts, accepts a run, and dies at the first completion. → interactive browser flow

2 · A minimal baseline

Skip every optional integration. Boot, confirm the gateway comes up on :8642, stop there — so anything that works later is something turned on knowingly. → nothing to store

3 · Eyes on the world

Get a Tavily API key, get the web tools switched on, and select tavily as the web backend. → ~/.hermes/.env + config.yaml

4 · Hands on the repos

A GitHub personal access token, authenticated through the gh CLI — which Hermes installed for itself. → the CLI's own credential store, outside ~/.hermes entirely

Step 0 — The host: a desktop image doing a server's job

Before any of that, there is a machine. It is a base Ubuntu Desktop image on its own box — and two of its defaults are actively wrong for something that has to sit there and answer requests. Both had to be undone by hand, and neither is a Hermes problem: a desktop image assumes a person is sitting at it. An agent host assumes nobody is.

Sleep had to be switched off

Ubuntu Desktop suspends an idle machine by default. For a workstation that's a feature; for this it is fatal, and it fails silently. A suspended box drops off the network, so:

  • the gateway stops answering on :8642 — gaca-api's adapter gets connection errors, not a useful failure;
  • the in-process cron scheduler stops firing, so scheduled jobs don't run late — they just never run;
  • an in-flight run dies mid-turn, and its read_run task on the API side is left holding an orphan.

The symptom is "the assistant is sometimes dead," which is a miserable thing to debug precisely because everything looks fine once you touch the machine and wake it.

SSH had to be installed and enabled

Ubuntu Desktop ships no openssh-server — a headless box you cannot log into is not much use, so it was installed and enabled manually:

sudo apt install -y openssh-server
sudo systemctl enable --now ssh

Diagnostic worth keeping: before this, every port on the box answered Connection refused while ping succeeded perfectly. That pairing is conclusive — a refusal is the kernel sending RST, meaning the host is up and nothing is listening. A firewall would drop the packet and you'd get a timeout instead. Refused = no daemon; timeout = something in the way.

On turning sleep off properly The Settings → Power toggle only governs the logged-in session. A box can still suspend from the login screen, and a laptop still suspends on lid close. The belt-and-braces version masks the targets outright, which no session or lid event can override: 
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
systemctl status sleep.target        # expect: masked
CONFIRMED — still open Checked on the box: the sleep targets report static, not masked, so the GUI toggle was what got used. The chassis is a desktop, so lid-close is moot — but the login-screen path is still live. Running the mask line above closes it permanently.
Why this belongs on the page at all It looks like sysadmin trivia; it is actually the same finding as the GitHub PAT, one layer down. Sleep policy and sshd are host state that lives nowhere in the project — not in the flake, not in ~/.hermes, not in any config GACA writes. A perfectly reproducible artifact deployed onto a box that suspends is a broken assistant. So "distributable" needs a documented host-prerequisites checklist, not just a pinned build. This is also the clearest argument for the eventual NixOS move: services.openssh.enable = true and masked sleep targets are two declarative lines there, versus imperative steps here that can silently drift back.

Step 1 — Auth: OAuth against a ChatGPT subscription

Hermes reaches a model through a provider credential. The notable choice here was subscription OAuth rather than a metered API key: authenticate against an existing ChatGPT plan and let Hermes drive gpt-5.6-sol through it, instead of dropping a pay-per-token platform key into ~/.hermes/.env.

What this buys

  • No per-token bill. Usage rides a flat subscription instead of a metered balance — the failure mode is a rate limit, not an invoice.
  • No long-lived secret sitting in a dotfile. OAuth stores refreshable tokens rather than a permanent key.
  • It sidesteps the exact wall this box already hit on a metered key. From the live log: Your credit balance is too low to access the Anthropic API → credential pool: marking ANTHROPIC_API_KEY exhausted (status=400), rotating. That run died mid-turn. A subscription cannot run out of credit that way.

What it costs — and this one matters

  • OAuth is an interactive browser flow. A human opens a URL and approves. That is categorically different from writing a key into a file.
  • ADR 0001 assumes the adapter performs first-time setup by writing credentials into ~/.hermes/.env. That model covers API keys cleanly and does not cover OAuth at all.
  • Tokens expire and refresh. A stored API key is static; an OAuth session is a lifecycle the adapter has to survive — including re-auth after it lapses.
First real gap found by doing it manually This is the payoff of the slow path. Subscription OAuth breaks the "adapter writes the secret to a file" assumption in ADR 0001. The Android app cannot silently mint an OAuth session — at minimum it must hand the user a device/browser flow and then detect completion. So the AgentBackend port's credential surface needs two shapes, not one: store this credential (synchronous, adapter-writable) and begin an interactive auth flow (asynchronous, user-completed, pollable). Better to learn that now than after the port is frozen.

Step 2 — The minimal baseline

With auth in place the gateway boots, and that is deliberately all it does. Hermes discovers a large plugin surface at startup and enables most of it, but a registered plugin is not a working capability — it is an available slot. Nearly all of them stay inert until you supply a credential and select them.

What that separation looks like, from this box's own boot log:

Plugin 'web-brave-free' registered web provider: brave-free
Plugin 'web-ddgs'       registered web provider: ddgs
Plugin 'web-exa'        registered web provider: exa
Plugin 'web-firecrawl'  registered web provider: firecrawl
Plugin 'web-parallel'   registered web provider: parallel
Plugin 'web-searxng'    registered web provider: searxng
Plugin 'web-tavily'     registered web provider: tavily
Plugin 'web-xai'        registered web provider: xai

Eight web providers registered; zero selected. "44 enabled" counts plugins loaded into the process, not features the agent can use. The same boot logs capability checks failing closed — check_web_api_key … returned False, check_image_generation_requirements returned False; dependent tools will be unavailable this turn — which is the minimal posture working exactly as intended: unconfigured capability ⇒ the tool is absent from the turn, not present-and-erroring.

Worth stealing for GACA That failure mode — a capability with no credential simply does not appear in the toolset — is the right behavior, and it is what GET /capabilities in the Hermes Plan exists for. The app should render its feature surface from what the backend reports it can actually do, not from a hardcoded list that produces runtime errors.

Step 3 — Web search: a credential and a choice

Giving the agent the web was two writes to two different files, and they are separate on purpose:

The credential — a secret, so it goes in .env

echo 'TAVILY_API_KEY=tvly-…' >> ~/.hermes/.env

This alone is what switches the web tools on. Hermes gates web_search and web_extract behind a check function, check_web_api_key, that flips to true as soon as any backend has usable credentials. Each backend maps to its own env var — TAVILY_API_KEY, EXA_API_KEY, FIRECRAWL_API_KEY, BRAVE_SEARCH_API_KEY, SEARXNG_URL, and so on. Supply one and the tools appear in the next turn's toolset.

The choice — not a secret, so it goes in config.yaml

hermes config set web.backend tavily

Which persists exactly one thing:

web:
  backend: tavily

That split is the whole shape of Hermes configuration in miniature, and it is good news for the adapter: secrets go to .env, choices go to config.yaml, both plain mutable files under a relocatable HERMES_HOME. Swapping to exa or a self-hosted searxng later is one key plus one config write — not a reinstall.

Why web search was worth the detour

The real motivation: the browser is broken in the Nix build Web search is not a nice-to-have here — it is the fix for a concrete performance bug. Running Hermes from the flake (nix run .#hermes), the browser tools register but their checks fail: _browser_cdp_check and _browser_dialog_check both return False, because Chromium is not in the Nix closure. With no search backend configured, the agent reached for the browser instead and ate roughly 31-second timeouts per attempt. Configuring Tavily gave it a fast structured-search path and sidestepped the broken browser entirely. Packaging Chromium is the lower-priority fix; search is the lever that actually mattered.

Why Tavily

Tavily is built for agent retrieval — it returns cleaned, ranked, model-ready content rather than a page of links to scrape. That is the difference between a tool the loop uses in one hop and a tool that needs a second extraction step, which matters doubly here because the extraction fallback (the browser) is the thing that's broken.

Practically: a free tier makes it a zero-commitment trial, and the one-line web.backend swap means exhausting that tier is a config change, not a migration. searxng is the natural fallback if the free credits run dry — no key at all, at the cost of running one more service on the Pi. ddgs would be the other keyless option but isn't packaged in this closure.

TO CONFIRM The stated reason for reaching for Tavily was a favorable read on Nebius. Worth checking that association before it goes in writing — as far as this page can establish, Tavily and Nebius are separate companies. The choice stands on its own merits either way.

Step 4 — GitHub: personal access token through the gh CLI

The route chosen was deliberate: a personal access token, not a GitHub App and not an OAuth app. For a single-user, self-hosted assistant that is the right call — a GitHub App exists to let many users install a shared integration under an identity that isn't a person's. There is only one user here, the assistant acts as that user, and a PAT says exactly that with no installation flow, no app registration, and no webhook plumbing.

How it went in

  1. Create a scoped personal access token on GitHub with read/write across the surface the agent needs.
  2. Hermes installed the gh CLI onto the box itself — the agent used its own terminal tool to provision its own dependency.
  3. Authenticate gh with the token, which hands credential storage to the CLI rather than to Hermes.
  4. Validate read-only first — ask Hermes to list the public repos. It worked, which proves the whole chain end to end: model → terminal tool → gh → GitHub API → back through the run's SSE.

Validating with a read before trusting a token with write is the right instinct and worth keeping as a habit: a listing call exercises binary, credential, network path, and tool wiring all at once, and the worst case if something is misconfigured is an error message rather than a mutated repo.

The third credential shape — and the first one Hermes doesn't own Auth was a browser flow. Tavily was a key in ~/.hermes/.env. This one is neither: the token lives in gh's own credential store on the Hermes host — its config directory or, on a box with a keyring, the system keyring. It is not in ~/.hermes at all. Hermes reaches GitHub by shelling out to a CLI that is already authenticated, so the capability is configured by host state that Hermes neither owns nor can see. Backing up HERMES_HOME does not back this up. Moving HERMES_HOME to a new machine does not bring it along.

What this does to the adapter's job

Steps 1–3 fit ADR 0001's model: the adapter writes files under a relocatable HERMES_HOME. Step 4 does not fit it at all, and that is the useful part.

A capability can be a binary

"Configure GitHub" here means install a program and authenticate it, not write a config key. The adapter cannot express that as a file write, and GET /capabilities can't report it either — Hermes has no idea whether gh is logged in until a tool call succeeds or fails.

State outside the state dir

ADR 0001 leans on HERMES_HOME being the whole story. It isn't. Any tool that shells out to an authenticated CLI puts part of the deployment's identity somewhere else on the host — a real gap in the backup, migration, and "distributable artifact" story.

Nix packaging implication

gh arriving via the agent's terminal is mutable host state outside the flake. If GitHub is a real capability rather than an experiment, gh belongs in the Hermes closure — the same class of gap as the missing Chromium.

Two things to go back and tighten The agent installed its own software. Hermes reached for terminal and provisioned its own dependency — worth naming out loud, because the same shell now has a GitHub token sitting next to it.

"Read/write to most everything" is broader than the job needs. A token that can write across the account can force-push, rewrite history, or delete a repo — no exploit required, just a confidently wrong agent. Nothing to undo today; the follow-up is to narrow the token to the repos GACA actually touches once it's clear which those are. CONFIRMED The token is fine-grained (github_pat_…) rather than a long-lived classic ghp_ — the better of the two, since a fine-grained token can carry an expiry, and expiry is a lifecycle the adapter will eventually have to handle exactly like OAuth refresh.
A deviation from the plan, and it's fine The Overview's build-vs-buy table calls for the official GitHub MCP server under "tools / integrations." Reality took the gh CLI through the terminal tool instead. That is a reasonable trade — the CLI is one install with no server to run, no MCP wiring, and it covers the entire GitHub surface rather than a curated tool subset. The costs are worth stating: no per-tool scoping (an MCP server can expose read-only operations; a shell with gh exposes everything the token allows), and coarser audit — the Hermes Plan's audit trail sees a terminal call, not github.create_issue. If the audit timeline matters as much as that page argues, the MCP server becomes the better answer later. For getting access working today, the CLI won on effort and it was the right call.

Step 5 — Memory: the first adopted subsystem switched on

Everything up to here was access — a model, the web, the repos. Memory is the first step that turns on a subsystem the GACA plan has a named port for, so it is the first one where the setup choice and the architecture touch. The decision for now: use Hermes' out-of-the-box memory management rather than building or substituting anything.

memory:
  memory_enabled: true          # long-term memory across sessions
  user_profile_enabled: true    # persistent model of the user
  memory_char_limit: 2200
  user_char_limit: 1375
  nudge_interval: 10
  flush_min_turns: 6

Those are two distinct features sharing a config block. memory_enabled is the cross-session store — facts the agent chooses to keep. user_profile_enabled is a persistent model of you specifically, with its own separate character budget. Turning both on is the right call for a personal assistant; they're worth understanding as separate things because the adapter may well want to expose them separately later.

Two switches, two subsystems — and no command that does both Memory is not one setting. It is a tool-visibility decision and a subsystem-feature decision, held in different places and changed by different commands. Both are now done:

1 · Is the memory tool offered to the model? Governed by agent.disabled_toolsets, managed interactively with hermes tools.
2 · Is the memory subsystem itself running? Governed by the memory: block: 
hermes config set memory.memory_enabled true
hermes config set memory.user_profile_enabled true
The trap is that hermes tools silently does only the first. It is a tool manager, not a feature manager — it never touches the memory: block and gives no hint a second step exists. Enable it there alone and you get the tool visible to the model with the subsystem switched off: looks configured, stores nothing.

This is the third appearance of the same shape — a credential plus a backend choice for web search, a toolset plus a feature flag for memory. "Enabled" in Hermes is routinely two switches in two places, and no single command spans them. A direct requirement on the adapter: enabling a capability through MemoryBackend is a compound operation, and an implementation that writes only the obvious key will report success and do nothing. ADJACENT session_search and context_engine are still disabled; both are memory-shaped and worth a deliberate call rather than being left off by inheritance.
Where memories actually land — not where the plan assumed Confirmed by watching the disk after the first turn: Hermes writes memory as plain Markdown files under ~/.hermes/memories/. The user profile arrived first, as USER.md, with a sibling USER.md.lock. memory_store.db was never created.

That directly answers an open question the Hermes Plan left for build time — "does Hermes expose a memory HTTP API? If not, the adapter reads memory_store.db on disk". The real answer is neither: it reads a directory of Markdown. Which is the best of the available outcomes — human-readable, greppable, diffable, trivially backed up, and no database schema to reverse-engineer or contend with. But the .lock file means there is a concurrency protocol to respect: the adapter must honour it rather than reading or writing the files naively while Hermes has them open.

Why this one matters more than the others

It fills a port that was empty

The Hermes Plan defines a MemoryBackend port and says Phase 1 the HermesAdapter implements it by reading Hermes' own memory — its HTTP API if one exists, otherwise memory_store.db on disk. Until now that port had nothing behind it, so "adopt memory from the engine" was an untested claim. Switching it on is what makes it testable.

ANSWERED That page's open question — memory HTTP endpoint, or read the SQLite file? — turned out to be a false dichotomy. It is a directory of Markdown files (see below), which is a materially easier thing for gaca-memory to read now and to migrate off later.

There are two state axes, not one

Worth keeping straight, because conflating them produces confusing recall behavior: session-transcript continuity (what was said in this conversation) is a different axis from the global cross-session memory store (memory_store.db, scoped by X-Hermes-Session-Key). A brand-new session that still recalls a fact is demonstrating the second one.

GACA should model both independently — the API owns the transcript, while memory scope is its own key. Turning memory on is what makes that distinction observable.

A hole in the audit timeline to expect Memory writes surface as ordinary tool events (tool.started / tool.completed with tool=memory), so they land in the audit trail like any other tool call. Memory reads do not — retrieved context is injected into the prompt with no event emitted at all. So the timeline the Hermes Plan wants to be trustworthy will show what the assistant recorded but not what it recalled before answering. That's a genuine gap, it's inherent to reading through the engine rather than owning memory, and it's an argument for gaca-memory later — not a reason to avoid adopting now.

Step 6 — Reach: SSH access to a second machine

The architecture here is deliberate and worth stating plainly, because there was an alternative and it was not taken. Hermes stays on david-claw. Its terminal backend remains local. A second box — piservices, a Raspberry Pi running Ubuntu 24.04.4 on aarch64 — hosts other apps and APIs, and Hermes simply SSHes into it when something over there needs updating. The Pi is a target, not a sandbox: one agent, one home, many machines it can reach.

What that took, and it is a better setup than a hand-rolled one usually gets:

A dedicated, purpose-named key

~/.ssh/hermes_piservices_ed25519
  ed25519 · comment: hermes-agent@piservices

Not a reused general-purpose key. One key, one destination, one job — so revoking the agent's access to the Pi is deleting a single file, with nothing else caught in the blast radius. The naming makes it self-documenting a year from now.

A ~/.ssh/config host alias

Host piservices
    HostName piservices
    User david
    IdentityFile ~/.ssh/hermes_piservices_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3

Three of those lines are doing real work, not decoration — see below.

Why those config lines matter for an agent specifically The Host alias reduces the command to ssh piservices. That sounds cosmetic and isn't: the agent has to reproduce this command from memory on every future turn. A short, stable, flagless invocation is far more reliably repeated than a long one carrying -i, a user, and a hostname — and it means the connection details can change later without invalidating everything the agent has learned.

IdentitiesOnly yes prevents a real failure mode. Without it, SSH offers every key it can find in turn; on a box that accumulates keys, that can trip the server's MaxAuthTries and fail even though the correct key was present. Pinning one identity makes the auth deterministic.

The keepalives protect long jobs. ServerAliveInterval 30 with ServerAliveCountMax 3 stops a router or NAT table from silently dropping an idle-looking connection mid-build — precisely the kind of failure that would otherwise show up as an inexplicable truncated deploy.
The trade-off to name, not to fix The private key is unencrypted — it has to be, for unattended use. Combined with terminal.backend: local, this means the agent can read its own SSH key, because Hermes' shell runs as the same user that owns ~/.ssh. So the Pi's security boundary is exactly the boundary around david-claw, no tighter. That is inherent to the chosen shape, and the mitigations are ordinary ones rather than architectural: keep the key scoped to one destination (done), and give the david account on the Pi only the privileges the work actually needs.

It also adds another entry to the running list: ~/.ssh/ is now a second place holding deployment-critical state that lives outside ~/.hermes — joining the GitHub PAT in the system keyring. Back up HERMES_HOME and you still have neither.

Step 7 — The Pi becomes a real host

With reach established, Hermes built out piservices itself: nginx, Docker, cloudflared, and gh. But the raw list undersells it — what actually got assembled is a properly closed edge, with everything above Docker running as containers, and a real application already serving through it.

What is actually running

piservices-gateway-cloudflared-1cloudflare/cloudflared:2026.7.3noneThe tunnel — dials out to Cloudflare
piservices-gateway-nginx-1nginx:alpine127.0.0.1:8080Reverse proxy — loopback only

Two Compose projects — piservices-gateway (the edge) and calendarapp (the workload) — cleanly separated, so apps come and go without touching the gateway. Every container is restart: unless-stopped, so the whole stack survives a reboot unattended.

The ingress path is genuinely closed The full listening surface of the machine is 0.0.0.0:22 and 127.0.0.1:8080 — plus systemd-resolved on loopback. No :80. No :443. Nothing but SSH is reachable from the LAN, let alone the internet. Traffic arrives by exactly one route: 
Internet → Cloudflare edge → tunnel (outbound-initiated)
         → cloudflared container → nginx container (127.0.0.1:8080)
         → app containers (Docker network only)
The apps have no host port binding at all — they exist only on the Compose network, reachable by nginx and nothing else. This is precisely the edge model the plan specified — Cloudflare Tunnel with no inbound ports — now running on ARM hardware, before GACA depends on it. That de-risks a load-bearing assumption by proving it rather than diagramming it.

The permission model, and why containerising the edge is what makes it work

The headline is that Hermes updates and adds applications without needing sudo. Verified: sudo -n fails — david is in the sudo group but every escalation wants a password, and no human is at the prompt. Meanwhile docker ps succeeds as david via docker group membership.

This is the design decision, not a happy accident Had nginx and cloudflared been installed as ordinary system services, the agent would need sudo to touch /etc/nginx or reload a unit — and those commands would hang forever waiting on a password prompt nobody answers. Putting the edge in containers is exactly what converts "no sudo" from a limitation into a complete capability. Adding a site, changing a route, rolling the tunnel: all of it is now docker compose work against user-owned files, and the agent is fully autonomous over the entire stack rather than only the leaf apps.
Two things to stay clear-eyed about Docker group membership is effectively root. Anyone who can reach the Docker socket can start a container that mounts the host filesystem and write to it as root — docker run -v /:/host is the whole trick. So "Hermes has no sudo" is accurate about ergonomics but overstates isolation: the agent has a straightforward path to root whenever it wants one. That is the standard trade for any single-user Docker host, with no clean fix short of rootless Docker — worth recording rather than assuming away, because the real boundary is "trusted machine," not "unprivileged user."

There is a second, vestigial nginx — but not a second cloudflared. The apt-installed host nginx is genuinely running (systemd MainPID, master plus four workers) yet binds nothing, because /etc/nginx/sites-enabled/ is empty. The nginx serving traffic is the nginx:alpine container. Harmless today, a debugging trap tomorrow: editing /etc/nginx/sites-available/… and reloading will appear to do nothing, because the config that matters is mounted into the container. sudo systemctl disable --now nginx leaves exactly one nginx on the box — a rare case where a little sudo now buys back a lot of confusion later.

The contrast is the lesson. Host cloudflared needs no such cleanup — its unit is already inactive and disabled. The difference is how each was installed: apt packages on Debian/Ubuntu auto-enable and auto-start on install, so apt install nginx silently leaves a running, boot-enabled service behind; cloudflared arrived as a plain binary in /usr/local/bin, so nothing started on its own. When an agent provisions a host, the package manager it happens to use decides whether you inherit a stray daemon — which is precisely the kind of invisible side effect a host-prerequisites manifest has to account for. LOOSE END /etc/cloudflared/token also survives from a cloudflared service install: a real tunnel credential on disk for a service that never runs. Confirm the container takes its token from the Compose config, then it can go.
What this adds to the adapter picture This step involves no Hermes configuration whatsoever — no key in .env, no value in config.yaml. It is capability existing purely as the state of another machine: which packages are present, which groups a user is in, which containers are running. Nothing in ~/.hermes records any of it and GET /capabilities can never report it. It is the strongest form yet of the pattern this page keeps hitting — a distributable GACA artifact needs a host-prerequisites manifest that reaches beyond its own machine, or a first-run probe that checks for these things and reports plainly what is missing.

Step 8 — Telegram: a temporary front door

Until gaca-api and the Android app exist, there is no way to talk to the assistant away from the box. Telegram fills that gap as an explicitly temporary front end — a bot token from @BotFather, an allowlist, and a home channel, all in ~/.hermes/.env:

TELEGRAM_BOT_TOKEN=…      # from @BotFather
TELEGRAM_ALLOWED_USERS=…  # allowlist — who may talk to it
TELEGRAM_HOME_CHANNEL=…   # where unprompted / scheduled output lands

Hermes treats it as a first-class gateway platform, exactly like api_server: platform_toolsets.telegram gives it its own toolset (hermes-telegram), so the two front ends run side by side against the same agent, sessions, and memory.

Two things worth taking from this The allowlist is the security model. A Telegram bot is reachable by anyone who finds it — unlike the gateway, which binds loopback and sits behind a bearer token. TELEGRAM_ALLOWED_USERS is the only thing standing between a stranger and an agent that has a shell, a GitHub token, and SSH into the Pi. Earlier boot logs warned about exactly this ("platforms default to pairing/allowlist policies and will deny unknown senders") — it matters far more now than when api_server was the only platform.

It validates the multi-platform shape ahead of time. gaca-api will be one front end among several rather than the only one — and TELEGRAM_HOME_CHANNEL is a preview of a problem GACA inherits: when a scheduled job or an unprompted message fires, which client should it reach? Hermes answers with a configured home channel. GACA will need its own answer.

Step 9 — Google Workspace: the first capability delivered by a skill

Everything so far was configured through Hermes — a flag, a key, a backend name. Google is different: the capability arrives as a skill (skills/productivity/google-workspace/, a SKILL.md plus helper scripts), and the decision was to lean on it rather than wire the APIs by hand — the skill authors clearly knew the terrain better than a first-time integrator would.

What that took on the Google side, all of it outside Hermes entirely:

  1. Create a dedicated Google Cloud project — Hermes.
  2. Enable the Gmail, Drive, Sheets, and Docs APIs on it.
  3. Create an OAuth client.
  4. Set the audience to testing rather than published — no Google verification review, which for a single-user assistant is the right call.
  5. Complete the consent flow and let the skill store the resulting credentials.

The friction was real and worth recording: copying values between the Cloud console and Hermes was fiddly, and it took a few attempts before it took. That is a data point, not a complaint — this is the step a user is most likely to abandon, so whatever GACA eventually does here needs to be markedly smoother than a chain of copy-pastes.

The testing-audience expiry trap An OAuth client left in testing mode issues refresh tokens that Google expires after seven days. The assistant will simply stop being able to read anything roughly a week from consent, and the symptom is an auth failure deep inside a skill rather than an obvious "your token expired." Two ways out: re-consent when it lapses, or move the app to published/in production — which for a single-user app using only these scopes is a formality rather than a review. Worth deciding now instead of debugging it next week.
What the skill route means for GACA This is the first capability that arrived as a SKILL.md plus scripts rather than a config value — which is the Hermes Plan's "skills come free with the engine" claim finally being exercised. Two consequences for the adapter: the credentials live at paths the skill chose (HERMES_HOME/google_token.json), so provisioning Google means satisfying a skill's private contract rather than writing a documented Hermes setting; and the capability is invisible to GET /capabilities, since it is a skill's own concern. A skill-delivered capability is a third configuration shape, alongside .env secrets and config.yaml choices — and the one furthest outside the adapter's reach.

Step 10 — The agent-ready app: a pattern worth naming

With apps now running on the Pi, the question becomes how the agent works them. The answer that emerged is the most reusable thing on this page, and it generalises well past any one app. Call it the agent-ready application: an app that ships its own instructions for being operated by an agent, and issues its own credential for doing so.

The pattern in one line The app exposes an API, mints a scoped token for the agent, and hands out skills describing how to drive itself — the operator downloads those skills into the agent, and from then on the agent acts on the user's behalf against the app's public interface. No plugin written for the agent. No agent-side integration code. The app teaches the agent, not the reverse.

The four moving parts

1 · An API, self-describing at runtime

The app publishes a machine-readable contract — an OpenAPI document — and the skill tells the agent to fetch it before the first operation each session and treat it as the source of truth, rather than trusting endpoint paths it remembers.

That single instruction is what makes the integration durable: the app can add fields, move routes, or version endpoints, and the agent re-reads reality instead of failing against a stale memory. The contract is discovered, never hardcoded.

2 · An operator-minted token

The app has a dedicated endpoint that mints a long-lived bearer token scoped to one user, with a caller-chosen lifetime. The operator generates it from their own profile page while logged in — so issuing agent access is a normal, authenticated user action, not an admin or database task.

Crucially the agent never sees a password. It holds one revocable credential representing one user, which can be re-minted or expired without touching the account itself.

3 · Skills, packaged by the app

The app generates downloadable skill archives — each a SKILL.md written by the people who built the API. They cover the base URL, the auth header, the discovery step, the workflow, and the error contract (401 → stop and ask for a fresh token, don't retry).

Because the app builds them, they ship with the app and stay correct as it evolves. Compare the alternative: integration code living in the agent, drifting quietly out of date every time the API changes.

4 · A human-in-the-loop install

The operator downloads the skill and drops it into the agent's skills directory. Deliberately manual — the human is the trust boundary. Nothing is auto-discovered, nothing self-installs, and adding a capability is an act someone performed on purpose.

This is the same instinct as the rest of this page: capability arrives one knowing step at a time.

Why this inverts everything else on this page Every earlier step configured Hermes to reach outward — a key in .env, a backend name in config.yaml, a skill's private credential path. This one requires nothing of the agent at all. The app supplies the interface, the instructions, and the credential; the agent supplies only a place to put them. Which means the integration surface belongs to the app, and the same app works with any agent that can read a SKILL.md and send a bearer token — Hermes today, gaca-agent later, something else after that. It is the opposite of a plugin ecosystem: instead of every agent shipping an integration for every app, every app ships one description of itself for all agents.

What this means for GACA

A template for everything we build

Any future app on the Pi can be made agent-operable the same way: publish an OpenAPI doc, add a token-minting endpoint behind normal auth, write a SKILL.md, offer it for download. Repeatable, and it survives the engine swap because it depends on nothing engine-specific.

The security story is better

Per-app, per-user, expiring tokens the operator issues and revokes — a real improvement on the broad GitHub PAT and the passwordless SSH key. Every app gets its own narrow credential rather than the agent accumulating account-wide power.

It re-raises the audit gap

The agent's calls arrive as ordinary authenticated API requests, so the app's own logs become an audit trail — with a caveat: they show the user's token, not "the agent did this." Distinguishing agent traffic from human traffic is worth designing in early.

Two things to get right when repeating this Token lifetime is a real decision. A long-lived bearer token stored where an unsupervised agent can read it is a standing grant — convenient, and exactly why per-app scoping matters. Prefer the shortest lifetime that avoids constant re-minting, and make sure revocation genuinely works before relying on it.

The skills carry security instructions, so they must be followed. These SKILL.md files tell the agent never to print, log, or commit the token, and never to expose it in generated output. That is the right guidance — but it is guidance to a language model, not an enforced boundary. Treat it as defence in depth, and keep the token out of any output path that ends up somewhere public.

Step 11 — Making it start every time: user services for the dashboard

Hermes has a browser dashboard — a local web UI for driving the agent, watching runs, and generally living in the thing day to day. Starting it by hand after every reboot gets old immediately, so it needed to come up on its own. That turned into a small lesson about user-level background jobs on Linux.

Three things now start automatically, all as systemd user units (systemctl --user) rather than root services:

UnitWhat it runsRestart
hermes-dashboardthe browser UI, bound 127.0.0.1:9119 with --no-openon-failure
hermes-gatewaygateway run — the api_server platform and Telegramalways
hermes-tuia persistent terminal UI inside screen, reattachableon-failure

All three are enabled and wanted by default.target. The dashboard binds loopback only — consistent with the gateway, and correct: it is an unauthenticated local UI onto an agent with a shell, a GitHub token, and SSH into another box. It should never be exposed, and reaching it from elsewhere should be an SSH tunnel, not a bind-address change.

The bit that actually makes it work: linger A user service normally lives and dies with your login session — systemd starts your user manager when you log in and tears it down when the last session ends, taking every user service with it. On a box you mostly reach over SSH, that means the dashboard would die the moment you disconnected, and would never start at all after an unattended reboot. 
loginctl enable-linger david     # confirmed: Linger=yes
Linger is what makes a user manager persist without a login session — so the units start at boot and survive logout. It is the one non-obvious step, and skipping it produces the maddening symptom of services that work perfectly while you're watching and vanish when you aren't.
Why user units rather than a crontab or a root service All three approaches would "start it every time," but they are not equivalent:

vs. @reboot in a crontab — cron fires the command once at boot and then forgets it. If the dashboard crashes at 3am, cron will not notice. systemd's Restart= brings it straight back, and journalctl --user -u hermes-dashboard gives you the logs and history. For a long-running daemon, "supervised" beats "launched."

vs. a root/system service — the whole stack reads and writes ~/.hermes, which is david's. Running as root would mean either running with more privilege than the job needs or fighting file ownership forever. User units keep the agent running as exactly the user whose resources it operates — the same principle as no-passwordless-sudo on the Pi.
What this adds to the deployment picture This is more host state living outside HERMES_HOME: three unit files under ~/.config/systemd/user/, plus a linger flag in /var/lib/systemd/linger/. Nothing in ~/.hermes records that any of it exists — restore the state dir onto a fresh machine and you get the configuration back but nothing that runs. It is the same gap as the GitHub keyring entry and the SSH key, and it lands on the same conclusion: a distributable GACA needs its process supervision described somewhere. Worth noting the Full GACA Plan already assumes systemd units for gaca-api — this is that decision arriving early, at user scope, and it is the right rehearsal for it.

Step 12 — The build skill: the agent starts writing code

Everything so far gave the agent access — a model, the web, repos, memory, a second machine, apps to drive. This step gives it competence at a specific job. A personal build skill was pulled from damont/build and installed as david-build, and it is what actually lets the agent write code on the operator's behalf and stand up small apps that are usable straight away.

Why a skill beats a prompt for this "Build me an app" against a bare model produces something shaped by whatever the model felt like that day — a different stack, a different layout, a different testing story every time. A build skill fixes the conventions once and applies them every time. The agent stops improvising architecture and starts executing a house style, which is what makes the output maintainable by the person who asked for it rather than a plausible-looking pile. The value is less that the agent can code, and more that it codes the same way twice.

What the skill actually carries

It is not one instruction file — it is a reference library, and the structure is the interesting part:

A phased build order

Ten ordered phase documents, from project setup through backend foundation, domain, and testing, then frontend, then Docker and deploy, then cross-app concerns and agent auth.

This is the same instinct as this whole page: one deliberate step at a time, in an order that makes each step verifiable. It also gives long builds a natural place to pause and resume — a real concern when a single run has a turn budget.

Conventions and cross-cutting references

Alongside the phases sit topic references — conventions, file storage, background workers, auth — so recurring decisions are answered from a document rather than re-litigated per project.

Notably one phase covers agent auth and API — meaning apps built this way come out agent-ready by default, with the token-minting and self-describing-API pattern from Step 10 baked in rather than retrofitted.

The stack it encodes — FastAPI + React + Docker — is the same one the apps on the Pi already run, which is what makes the whole loop close: the agent builds in the shape the host is already prepared to serve.

The second skill is the clever bit

Installed alongside it is david-build-update, whose only job is to refresh david-build from newer commits in the source repo — and it tracks its own progress in a small state file:

{
  "repo": "…", "remote_url": "https://github.com/damont/build.git",
  "branch": "main",
  "last_used_commit": "9e2fdd2…",
  "updated_at": "2026-08-06T12:58:17Z"
}
Why the pairing matters more than either skill alone A skill copied into an agent is a fork the moment it lands — the upstream conventions improve, the installed copy doesn't, and it silently rots. That is the standard failure mode of copy-in integrations, and it is the same problem the Step 10 pattern solves for APIs by making the agent re-read the contract.

Recording last_used_commit turns updating into a bounded, incremental diff — "what changed since the commit I already absorbed?" — rather than a re-read of the whole repo or a blind overwrite. The agent maintains its own capability, with a checkpoint. That is a genuinely reusable idea: any skill sourced from a living repo should ship with something that knows how to update it and how far it has got.
Two things worth watching Skills are prompts, not code paths. A build skill improves consistency; it does not enforce anything. Nothing rejects output that ignores a convention, so the real check remains running the tests and reading the diff. Treat the skill as a strong default, not a guarantee — the same caveat as the security instructions carried in the Step 10 skills.

An updating skill executes what it fetches. david-build-update pulls from a remote repo and rewrites the instructions the agent will later follow, on a box where terminal is unsupervised. That is fine here — it is the operator's own repo, pinned to a known branch — but it is worth naming as a supply-chain path: whoever can push to that repo can change how the agent builds.
Where this lands for GACA This is the clearest instance yet of the Hermes Plan's "skills come free with the engine" claim paying off — and the format is portable. A SKILL.md plus reference documents is not Hermes-specific; the open skill format is exactly what the Overview proposed adopting. When gaca-agent eventually replaces Hermes behind the port, this skill library moves across unchanged. It is capability accumulating in a form that survives the engine swap — which is precisely what the adapter architecture was designed to protect.

When a manual step graduates

This is the arc the page is really about. One of the hand-typed hermes config set … commands above has already moved into the flake's gateway wrapper, so nix run .#hermes re-asserts them at every launch:

hermes-gateway = pkgs.writeShellScriptBin "hermes-gateway" ''
  # Batteries-included policy, enforced on every launch (idempotent,
  # self-healing — re-asserted each start so config can't drift).
  ${hermes}/bin/hermes config set web.backend tavily
  exec ${hermes}/bin/hermes gateway run "$@"
'';

Three things worth noticing about that:

It has to be a launch step

The Nix build is sandboxed and pure — it cannot write ~/.hermes. So policy can't be baked into the derivation; it is asserted when the wrapper runs. HERMES_HOME must stay writable for the same reason.

Only the choice, never the secret

The wrapper names tavily; it never contains TAVILY_API_KEY. That is ADR 0001's line held exactly — a distributable artifact can carry a default choice, never an operator's credential.

Idempotent by design

Re-running config set every launch means config can't drift out from under the deployment. This is the same shape the adapter's first-time-setup will take.

What this changes in the plan

Carry these forward
  1. The credential port needs an interactive mode. ADR 0001's "adapter writes the key" covers API keys only. Add begin interactive auth → poll status alongside store credential before the AgentBackend port is frozen.
  2. Capability config and secrets are separate writes (config.yaml vs .env) and should stay separate in GACA's own config API — different lifetimes, different exposure rules, and only one of them is safe to ship in an artifact.
  3. GET /capabilities is load-bearing, not a nicety. Hermes already drops unconfigured tools from the turn; the app should mirror that instead of hardcoding a feature list.
  4. Provider choice is one config key. Running out of Tavily free credits is an operational event, not an architectural one — searxng is a one-line swap.
  5. Launch-time assertion is the deploy pattern. Pure builds can't touch ~/.hermes, so batteries-included policy belongs in an idempotent wrapper — the same shape the adapter's first-time setup will take.
  6. HERMES_HOME is not the whole deployment. The GitHub PAT lives in another program's credential store, so backup, migration, and "distributable artifact" claims that assume the state dir captures everything are wrong. Either bring such credentials under a GACA-owned provisioning path or document them as host prerequisites — but don't let ADR 0001 keep implying they don't exist.
  7. "Distributable" needs a host-prerequisites checklist, not just a pinned build. A reproducible artifact on a box that suspends is a broken assistant. Sleep policy, sshd, and packaged CLI dependencies are all deployment requirements that live outside the flake — write them down, and treat them as the concrete case for the eventual NixOS move, where they collapse into declarative config.
  8. Shelling out to a CLI trades audit granularity for reach. The plan's audit timeline sees terminal, not the GitHub operation inside it. Acceptable now; revisit the MCP server if the timeline is meant to be trustworthy on its own.
