04 · GACA Plan

One repo, four components, the Pi as host

The build we're actually doing. One git repo (gaca/) with four components built under it: gaca-api (the front door and system of record), gaca-agent (the brain — it calls tools directly), gaca-memory (a dedicated memory system), and gaca-android (a native app). The API knows which tools exist and owns sessions, policy config, the audit trail, and long-term memory; the agent fetches that catalog and then executes tools itself, on the host, streaming audit back. There is no Docker — a Nix flake pins every dependency and systemd supervises each component.

What changed from the previous plan Three structural changes. (1) The agent calls tools directly. The old plan routed every side effect through POST /tools/{name}:execute on the API. Now the API only publishes the catalog of available tools; the agent executes them in-process against the host and streams audit events back. The agent is now the privileged component. (2) Memory is its own system. A dedicated gaca-memory service holds long-term memory (the API recalls/writes it) and short-term working memory (the agent loads it into the live session). (3) No containers. A Nix flake + systemd units replace docker-compose. The Android client also becomes a native app rather than a PWA.

And in this revision (4) Communication is async — the session is a timeline, not a request/response. POST /sessions/{id}/messages returns 202 instantly; the session event stream is the only return path. No request is ever held open. The agent is a long-running supervisor per session that stays snappy by streaming its progress as it works; heavy fan-out to background subagents is a later phase. (5) Two stores, one job each. MongoDB is the system of record (sessions, messages, audit, runs); Redis is pure transport — Streams for the run queue + per-session inbox, pub/sub for the event fan-out. (6) A React test UI (gaca-testui) is built alongside to exercise the API/agents while the native app comes together.

Guiding principles

The API is the front door & system of record

gaca-api is the single HTTP surface your phone talks to. It owns sessions, the tool catalog (definitions + schemas + policy config), the audit log, and access to long-term memory. It no longer executes tools or touches the OS for the agent. In front of it, Cloudflare (Tunnel + Access) is the outer gate — for a single-user app, an email allow-list means only you ever reach the API.

The agent is the hands

gaca-agent fetches the tool catalog from the API, then runs each tool itself, directly on the host. It loads short-term memory into its session, drives the model loop, and streams events + audit entries back to the API.

Memory is a dedicated system

gaca-memory is its own service. Long-term memory (durable facts, semantic recall) is read/written by the API. Short-term working memory is loaded into the agent's session and flushed back at the end of a run.

No containers — Nix + systemd

A single Nix flake pins all dependencies and builds each component reproducibly. systemd units run them as supervised, auto-restarting services on the Pi. nix build + systemctl is the whole deploy.

The four components

One repo, four components side by side, plus a shared schemas/ package that is the contract between them.

gaca-api the front door

One FastAPI app. The single HTTP surface for the phone and the agent. Owns sessions + audit (MongoDB), publishes the tool catalog, brokers long-term memory, enforces auth. Never blocks — it dispatches work and streams results back.

  • All client-facing endpoints, grouped by resource
  • MongoDB (local) for sessions, messages, audit, runs
  • Dispatches runs via Redis Streams; fans events out via Redis pub/sub → SSE
  • Auth: single-user API key for clients; service token for the agent
  • Publishes the tool catalog — it does not run tools

gaca-agent the brain + hands

Its own service. A Pydantic AI Agent supplies tool-calling + model machinery. It pulls the catalog from the API and executes tools directly on the host. A long-running supervisor per active session.

  • Stays alive per session — answers instantly, delegates the slow work
  • Tools run in-process, against the box (fs, cli, procs, …)
  • Spawns background subagents (non-blocking); their results arrive as events
  • Loads short-term memory from gaca-memory into the session
  • Streams events + audit entries back to gaca-api

gaca-memory the memory

A dedicated service with its own store (Mem0 + sqlite-vec). Holds both tiers of memory and serves two clients.

  • Long-term: durable facts + semantic recall — read/written by the API
  • Short-term: per-session working set — loaded/flushed by the agent
  • Promotion: salient short-term items get written to long-term on close
  • One system to own embeddings, retention, and recall policy

gaca-android the client

A native Android app (Kotlin + Jetpack Compose) reaching gaca-api through Cloudflare (Tunnel + Access). Replaces the earlier PWA plan.

  • Text, audio capture, image + file attachments
  • Streams session events (SSE/WebSocket) for live replies
  • Stores the API key in the Android keystore
  • First-class share-sheet, mic, and notification access

How the agent and API communicate — async by default

The API never holds a request open. The session is a timeline, not a request/response pair: your message goes in, the API acknowledges instantly, and everything the agent produces — tokens, tool calls, "I've kicked off X," a subagent result that lands 40 seconds later — comes back on a single event stream. That's what keeps it snappy even when the answer isn't ready yet.

Inbound is non-blocking

POST /sessions/{id}/messages persists the message to Mongo, XADDs a run to a Redis Stream, and returns 202 Accepted with a turn id — immediately. No waiting on the agent.

The event stream is the only return path

The phone is already subscribed to GET /sessions/{id}/events (SSE). It renders whatever appears, whenever it appears. There is no "response" to wait for — just the timeline filling in.

The comms substrate between the two services is Redis — pure transport, with MongoDB as the system of record behind it. There are two distinct dispatch channels, each with one job:

  • Route signal (shared, API → agent service): when a session needs attention, the API XADDs a lightweight "ensure session S has a live supervisor" signal to a shared dispatch stream. The agent service consumes it with XREADGROUP ... BLOCK 0 (consumer group + XACK, at-least-once) and, if no supervisor is alive for S, spawns one. This stream carries routing/spawn signals, not messages.
  • Per-session inbox (the message path): the actual message is XADDed to a per-session stream (inbox:{session_id}) that the live supervisor for that session reads in order. Your typed messages flow here — and later, subagent results too. One ordered queue per session, drained by exactly one supervisor.
  • Return path (agent → frontend): the agent POSTs each event + audit entry to the API. The API does two things with it — persist to Mongo (the durable log) and publish to a per-session Redis pub/sub channel. Every open GET /sessions/{id}/events handler is subscribed to that channel, so it flushes the event straight down the already-open SSE connection to the phone.

That last point answers "how does the agent's reply reach the frontend": the agent never talks to the phone — it posts to the API, the API persists-then-publishes, and Redis pub/sub fans the event out to every subscribed SSE stream. Because the event is in Mongo first, a phone that was disconnected replays what it missed (by last-seen event id) on reconnect, then resumes live. And because the fan-out is Redis pub/sub rather than an in-process queue, it keeps working even if the API runs more than one worker.

The supervisor: lifecycle and Phase-1 scope

The agent is a long-running supervisor per active session. It owns the live context, so it can answer a turn and keep going instead of being rebuilt per request. It is not immortal, though — it has a defined lifecycle:

Spawned on demand

The shared dispatch stream's only job is routing: when a message arrives for session S and no supervisor is alive for it, the agent service spawns one. Exactly one supervisor owns session S and drains its inbox:{S} stream in order.

Idle-timeout + rehydrate

After a quiet period the supervisor flushes its short-term memory and exits (no idle processes). The next message for S routes through dispatch, a fresh supervisor spawns, and it rehydrates from Mongo (recent turns/state) + gaca-memory (short-term working set) before it answers.

Both your typed messages and (later) subagent results are just inputs on that one serialized inbox:{S} stream, drained in order — so a genuinely concurrent situation (you typing while work lands) never becomes a race.

Phase 1: supervisor + tools only — it narrates instead of fanning out Phase 1 ships just the supervisor and direct tool-calling. There are no real subagents yet. Instead, the supervisor streams its progress as it works ("checking the repo… found the config… running the build…") so you see and understand what it's doing in real time. This mimics the responsiveness of fan-out without the machinery, and — for a learning-oriented build — keeps the agent's reasoning visible rather than hidden inside a subagent.
Later: real subagents + a triage rule When fan-out lands, spawn(task) returns a task_id immediately (non-blocking); the subagent is its own loop with its own context + scoped catalog, and XADDs its result back to inbox:{S}, surfaced at the next turn boundary. Spawning has a tax (fresh context, model warm-up), so the supervisor triages:

Inline (do it now)

Fast, read-only, deterministic, or needed for the next sentence: fs.read, search.grep, a quick cli.run, a memory lookup.

Spawn a subagent

Slow, uncertain, parallelizable, context-heavy, or "I can answer you while this runs": repo audits, multi-step research, coding tasks, long network work.

Plus the guardrails that make fan-out safe: a max-concurrent-subagents cap per session, cancellation, and a task registry (/tasks) surfaced on the phone.

Memory, the two tiers

Long-term via gaca-api

Durable facts, preferences, and summaries with semantic recall (Mem0 + sqlite-vec). The API recalls relevant memories when a session starts and writes new durable facts when one closes. Clients can also query it through /memory.

Short-term in the agent session

The working set / scratchpad for the active run: recent turns, intermediate results, the current task's state. The agent loads it into the session context at run start, updates it during the run, and flushes the salient parts to long-term at the end.

Why a dedicated system: keeping embeddings, retention, promotion (short → long), and recall policy in one service means neither the API nor the agent grows a memory subsystem of its own — they're both just clients of gaca-memory.

The default toolset

Tools run inside gaca-agent, directly on the host. Phase 1 ships a small, high-leverage set. Each is declared in the API's catalog (name + JSON schema + policy scope) so the agent knows what's available and the model knows how to call it.

Rounding out the set: code search (grep/glob) so the agent finds things cheaply; process management so it can run a server/build and watch it, not just fire one-shot commands; http fetch + web search so it can read the live web; and git/gh because almost every useful task touches a repo. Deferred to later phases: MCP tools (Gmail read, Calendar write, Drive read), subagent spawn (coding/other), and image/attachment handling.

Trust trade-off — the agent is now privileged Because the agent executes tools directly on the host (no central pre-execution gate), gaca-agent is the component that touches the OS. Phase-1 guardrails are local and code-level: a working-directory jail, a tool allow-list the agent honors, and the audit stream to the API so you can always see what ran. Real isolation for risky/subagent work — bubblewrap + ephemeral worktree (no Docker), egress allow-list — is a later phase. See Architecture. This is an open question flagged below.

Because it's one repo, schemas/ is a plain shared package the Python components import — no copy-paste, no version skew. The boundary that matters is the dependency rule: the agent reaches the API only over HTTP, never by import; they share data shapes, never logic. gaca-android (Gradle) and gaca-testui (npm/Vite) are separate toolchains inside the same repo — the flake's dev shell provides both.

The agent, in pseudocode

# gaca-agent — the service ROUTES; a per-session supervisor does the work. Tools run HERE, on the host.
agent = Agent(model, system_prompt=BASE)

# --- router: one consumer group on the shared dispatch stream (signals, not messages) ---
async def route():
    async for sig in xreadgroup("dispatch", group="agents", block=0):   # wakes instantly, at-least-once
        if not supervisor_alive(sig.session_id):
            start_supervisor(sig.session_id)        # spawn ONE supervisor on demand
        xack("dispatch", sig.id)

# --- one long-running supervisor per active session ---
async def supervise(session_id):
    catalog = await api.get("/tools")               # policy-scoped catalog (names + schemas)
    short   = await memory.load(session_id)         # rehydrate short-term working set
    history = await api.get(f"/sessions/{session_id}")   # rehydrate recent turns from Mongo

    async for msg in xread(f"inbox:{session_id}", block=IDLE_TIMEOUT):  # THE message path
        if msg is None:                             # idle: flush short-term + exit (no idle procs)
            await memory.flush(session_id); return
        ctx = build_context(catalog, short, history, msg)
        async with agent.run_stream(ctx) as stream:
            async for event in stream:
                await api.post(f"/sessions/{session_id}/events", event)  # persist + relay

@agent.tool
async def fs_read(ctx, path: str) -> str:           # an INLINE tool — runs now, returns now
    policy.check("fs.read", path)                   # local allow-list + working-dir jail
    result = read_file_on_host(path)                # executes DIRECTLY on the host
    await api.post("/audit", tool_call("fs.read", path, result))  # STRUCTURED audit — never prose
    return result

# LATER PHASE — non-blocking fan-out:
# @agent.tool
# async def spawn(ctx, task, kind):                 # returns a handle immediately, not a result
#     run = await api.post("/agents/runs", {"parent": ctx.session, "task": task})
#     return {"task_id": run.id}                    # subagent XADDs its result back to inbox:{session}

Pydantic AI supplies agent.run_stream and the tool-call plumbing. What makes it ours: a router that spawns one supervisor per session on demand, a supervisor that rehydrates and drains one ordered inbox (and exits when idle), tools that execute on the host behind a local policy check, a structured audit entry on every effect (so intent is never lost in prose), and short-term memory framing the session.

Locked decisions

The constraints any work on GACA must honor. This list is canonical — if code or a suggestion conflicts with one of these, the decision wins unless it's explicitly changed here first.

Honor these
  1. One repo, four components. gaca-api/, gaca-agent/, gaca-memory/, and gaca-android/ under a single git repo (gaca/), plus a shared schemas/ package. No second repo.
  2. No Docker. A Nix flake pins all dependencies and builds each component; systemd units run them. nix build + systemctl is the deploy. New infrastructure is added as more Nix packages + systemd units.
  3. The API is the front door and system of record. Every client-facing capability is an HTTP endpoint on gaca-api, grouped by resource (/sessions, /agents, /tools, /skills, /audit, /memory; later /approvals). It owns sessions, the tool catalog, policy config, the audit log, and long-term memory access.
  4. The API publishes the tool catalog; it does not execute tools. GET /tools returns the policy-scoped list of available tools and their schemas. There is no :execute endpoint.
  5. Cloudflare is the network edge. Clients reach gaca-api only through Cloudflare (Tunnel + Access); an Access policy with an email allow-list (single user) is the first gate, in front of the API's own app-layer auth. No port on the Pi is exposed directly to the internet.
  6. The agent executes tools directly, on the host. gaca-agent runs each tool in-process against the box, enforces a local policy (working-dir jail + allow-list), and is the privileged component that touches the OS.
  7. Every tool call is audited. The agent streams an audit entry to POST /audit for each tool it runs. The audit log is on from day one.
  8. Communication is async; no request is held open. POST /sessions/{id}/messages returns 202 immediately; the session SSE event stream is the only return path. All output — tokens, tool calls, subagent results — arrives on that timeline.
  9. The agent is a long-running supervisor, one per session, spawned on demand. A shared Redis dispatch stream (consumer group) carries route/spawn signals only; the message path is a per-session inbox:{session} stream the supervisor drains in order. The supervisor idle-times-out (flushing short-term memory) and rehydrates from Mongo + gaca-memory on the next message. Phase 1 ships the supervisor + direct tools only and narrates progress inline; spawn/subagents are a later phase.
  10. The agent reaches the API only over HTTP, never by import — components share data shapes via schemas/, never logic. Session-message transport runs over Redis, but the agent does call the API for state (tool catalog, run records, audit, long-term memory). Those calls are typed/structured (shared schemas), so what the agent is doing is captured as data — never lost in plain English. (The exact catalog of state calls is a boundary to refine in practice.)
  11. The agent is built on Pydantic AI — chosen as the most straightforward option with the least framework baggage. It supplies tool-calling and model machinery; we own the host tool impls, the local policy, the audit stream, and memory wiring.
  12. Memory is a dedicated system. gaca-memory holds long-term memory and short-term working memory. Clients write durable (long-term) facts through the API (it's state); the agent loads/flushes short-term directly. Promotion (short→long) is internal to gaca-memory, run on flush (idle-timeout or session close). Neither the API nor the agent grows its own memory store.
  13. MongoDB is the system of record; Redis is the transport. Application data/state lives in local MongoDB — the API works in objects, MongoDB is already used elsewhere, and document storage fits app state. (Internal or speed-critical data may later use SQLite/Postgres where objects aren't the point.) Redis is pure transport: the shared dispatch stream + per-session inboxes are Redis Streams, the event fan-out is Redis pub/sub. gaca-memory owns its own store. The Pi is the Phase 1 host; tools run directly on the box and real sandbox isolation (bubblewrap, no Docker) is deferred.
  14. The client is a native Android app. gaca-android (Kotlin + Jetpack Compose) reaching the API through Cloudflare — not a PWA. A React gaca-testui is built alongside as a dev/test client and is not the shipping UI.
  15. Everything beyond Phase 1 is additive. Approval gate, sandbox isolation, scheduler, MCP, subagents, and the LiteLLM gateway bolt on without reshaping the four components.
