03 · Hardware & Models

The Pi runs the agent. It does not run the brain.

Your instinct was exactly right: the Raspberry Pi 5 is a fine orchestration host but a poor inference host. The good news — the standard 2026 pattern splits those cleanly, and a model gateway makes "local vs provider" a one-line flip. So you can be local-first today and stay all-local later by adding one box.

What a Pi 5 can actually run

CPU-only ARM, no real GPU, memory-bandwidth bound. Only tiny models are interactive — and crucially, most of them fail at tool/function calling, which is the one thing an agent needs.

Reality check In a real Pi-5 benchmark, function/tool calling failed on most small models (only BitNet 2B and SmolLM2 succeeded) and 5,000-token inputs timed out. Treat an on-Pi LLM as an offline fallback for trivial chat — not the agent's reasoning engine. Get the 16GB Pi 5 with active cooling.

The split: orchestrate on the Pi, infer elsewhere

This is clean and standard because the OpenAI Chat Completions API is the universal wire format — Ollama, vLLM, and every provider speak it. Nothing in your architecture changes when you swap the target.

On the Pi (cheap, always-on)

  • Agent loop + API + auth
  • Memory (sqlite-vec / Chroma)
  • Tool routing + MCP clients
  • Scheduler / cron
  • LiteLLM proxy (lightweight — runs here)

Inference target = any base_url

(a) Local GPU box on your LAN via Ollama's OpenAI-compatible API:

base_url = "http://192.168.x.x:11434/v1"
api_key  = "ollama"   # any non-empty string

(b) A provider — same interface, different base_url + key. That's the whole difference.

The swap layer: LiteLLM

Point your loop at one LiteLLM endpoint. Routing, fallback, keys, and budgets live in a config file. Swapping local↔provider is a one-line alias change — and you get automatic failover.

model_list:
  - model_name: local-qwen            # your alias
    litellm_params:
      model: ollama/qwen3-coder:30b
      api_base: http://192.168.x.x:11434
  - model_name: cloud-big
    litellm_params:
      model: anthropic/claude-...      # or deepseek / openai / etc.
      api_key: os.environ/PROVIDER_KEY

# fallback: try local first, fail over to cloud
router_settings:
  fallbacks: [{"local-qwen": ["cloud-big"]}]

Your agent always calls model="local-qwen". This is your "open source models or a provider if desired" requirement, solved with config instead of code.

Key trick: MoE models run dramatically faster on these boxes than dense models of similar size.

Best small/medium models for agentic tool-use (2026)

Top local pick

Qwen3-Coder-30B-A3B (MoE, 3B active). Explicitly strong at tool calling, ~100 tok/s on Strix Halo, fits 24GB at Q4. Tool-calling now works cleanly in llama.cpp/Ollama/LM Studio. Best local agent brain right now.

Runner-up

gpt-oss-20b (OpenAI open-weight MoE). ~33% more memory-efficient than Qwen3-30B on consumer GPUs, native tool-use, trivial in Ollama. Slightly less reasoning depth, more speed/footprint.

Smaller / between Pi and 30B

Qwen3 4B / 8B / 14B dense — solid agentic small models; 8B/14B run on a 3090 or Mac Mini. Gemma 3/4 (12–31B) good for single-file coding/refactor. Mistral Small 4 (~24B, Apache-2.0) for fine-tuning.

Frontier (use via provider)

DeepSeek V4, Kimi K2.6, Qwen 3.6 Plus, GLM-5.1 lead agentic-coding leaderboards but are 100B+ MoE — too big for a personal box. Consume these through the provider slot in LiteLLM when a task needs the horsepower.

Test in your harness Benchmark scores ≠ real tool-calling reliability. Before committing to a local model, run it inside GACA with your actual tool schemas and retry logic. The model that benchmarks best isn't always the one that calls your tools most reliably.

Recommended progression

Phase 1 — now

Pi 5 (16GB) runs the loop + LiteLLM. Inference → a provider (cheap to validate the whole agent). Keep a 1.5B local model as offline chat fallback.

Phase 2 — local-first

Add a used 3090 box (or Strix Halo) running Qwen3-Coder-30B-A3B. Add it to LiteLLM as the primary, provider as fallback. Now you're local-first with a one-line escape hatch.

Phase 3 — tune

Route by task: small/local for routine tool calls, provider (or a bigger local box) only for hard reasoning/coding. LiteLLM makes this a config policy, not a rewrite.

Nothing about the architecture changes between phases — that's the point of the gateway.
